# Пилот №16: «Единица заботы» (care unit)

Проверка идеи из [`../05-mozgovoy-shturm-arhitektura-i-vizualizaciya.md`](../05-mozgovoy-shturm-arhitektura-i-vizualizaciya.md#вопрос-2--про-больницу-дом-престарелых-tierheim-и-приют-для-бездомных-пункты-3-4-5-6):
один и тот же контракт данных описывает и резидента дома престарелых, и животное
в приюте (Tierheim), и человека в приюте для бездомных — меняется только
**словарь потребностей** и подписи, форма контракта одна.

## Файлы

| Файл | Роль |
|---|---|
| `care-unit.schema.json` | Формальная JSON Schema (2020-12) — контракт «единицы заботы». |
| `primer-dom-prestarelyh.json` | Инстанс: `domain: "elderly_care"`, резидент/комната — тот же словарь потребностей и цвета светофора (2/5 минут), что в [`../03-pult-upravleniya-uhod.md`](../03-pult-upravleniya-uhod.md) и в `../demo/pult-nuzhd-demo.html`. |
| `primer-tierheim.json` | Инстанс: `domain: "animal_shelter"`, животное/вольер — новый словарь потребностей (корм, вода, выгул, ветеринар, статус усыновления), пороги эскалации в минутах, но другие (15/60 — животное не может нажать SOS само, поэтому пороги мягче, а вот «нужен ветеринар» помечен `danger` по умолчанию). |
| `primer-priyut-bezdomnyh.json` | Инстанс: `domain: "homeless_shelter"`, человек/койко-место — третий словарь потребностей (душ, документы, талон на еду, комендантский час, конфликт), пороги эскалации в часах, а не минутах — процесс здесь медленнее, чем физиологическая нужда, но быстрее, чем бюрократический процесс из пилота №15 (там пороги — в рабочих днях). |
| `validate.py` | Компактный валидатор на чистом stdlib (без `pip install jsonschema`) — проверяет все три примера на соответствие схеме. |

## Проверка

```sh
cd docs/dostupnost-dlya-invalidov/pilot-16-edinitsa-zaboty
python3 validate.py
```

Ожидаемый вывод — три `✓`. Валидатор реально ловит ошибки (проверено вручную:
удаление обязательного поля и подстановка значения вне `enum` дают три
конкретных сообщения об ошибке, а не молчаливое `OK`).

## Что здесь единое, а что различается по доменам

| | Единое (в схеме) | Разное (в примерах) |
|---|---|---|
| Форма контракта | `subject`, `private_space`, `needs_vocabulary`, `caretaker`, `schedule`, `escalation` | — |
| Словарь потребностей | Формат элемента (`id`, `icon`, `label_ru`, `urgency_default`) | Сам набор потребностей — три разных словаря под три домена |
| Эскалация | Формат (`unit`, `warn_after`, `danger_after`) | Единицы измерения и числа: минуты для физиологии, часы для быта в приюте, дни для бюрократии (пилот №15) |
| Пространство | Поле `private_space.kind` | `room` / `kennel` / `bed` |

## Как это соединяется с остальными пилотами и документами

- `needs_vocabulary` из `primer-dom-prestarelyh.json` — то же самое множество
  потребностей, что уже реализовано интерактивно в `../demo/pult-nuzhd-demo.html`
  (документ 03). Панель ухода можно рассматривать как UI поверх ровно такого
  JSON, просто пока зашитого прямо в код демо, а не загружаемого из файла.
- Пороги эскалации `escalation.unit: "days"` из пилота №15 (заявки `soz30`) —
  тот же формат `{unit, warn_after, danger_after}`, что и здесь; можно
  добавить `"domain": "benefit_application"` четвёртым значением `enum` и
  описать заявку на Haushalt Assistenz как ещё один инстанс этой же схемы.
- `schedule` — прямой вход для пилота №19 (временной тессеракт): расписание
  каждой «единицы заботы» — это как раз те точки, которые должны «зажигаться»
  на 3D-плане здания при перемотке времени.

## Что дальше, если пилот приживётся

1. Добавить в `enum` домена `"benefit_application"` и описать пилот №15 через
   ту же схему (сейчас они рядом, но формально не связаны одним контрактом).
2. Написать один общий UI-компонент (расширение `pult-nuzhd-demo.html`),
   который рендерит панель потребностей **из любого** `primer-*.json`,
   подставляя нужный словарь — вместо трёх переписанных с нуля панелей под
   три домена.
