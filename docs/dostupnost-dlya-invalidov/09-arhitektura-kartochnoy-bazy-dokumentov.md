# Архитектура «карточной» базы документов: что уже есть и что строить

> Вопрос: ПО «как множество карточек-визиток», похожее на вики, в markdown-
> формате, умеющее «исполнять файлы» — какой оптимальный формат/схема/
> алгоритмы для базы, где серьёзные документы (не только параграфы законов,
> но и, например, почасовая ставка) нужно сравнивать между собой — как
> из того, что сделано в `soz30`, сделать динамическое приложение для
> десктопа/мобильного, какая архитектура. Проверено веб-поиском (сентябрь
> 2026) + собственная архитектурная рекомендация, основанная на пилотах
> №15/№16 из этой же папки.

## Как называется то, что вы описываете

То, что вы описываете — это классический **Zettelkasten** («картотека
карточек», метод Никласа Лумана): много маленьких заметок-карточек, связанных
ссылками, а не разложенных по строгим папкам. Современные markdown-приложения
для этого называются **PKM** (Personal Knowledge Management). «Исполнять
файлы» — это уже следующий слой, который не все PKM-инструменты умеют.

## Готовое ПО, которое ближе всего к описанному (реально существует, проверено)

| Инструмент | Markdown-файлы на диске | «Карточки»/база с полями (почасовая ставка и т.п.) | Исполнение кода внутри | Десктоп | Мобильный |
|---|---|---|---|---|---|
| **Obsidian + Dataview** | ✅ да, `.md` + YAML frontmatter | ✅ Dataview: frontmatter автоматически становится полями запроса (DQL или JS); с 2025 года в само приложение встроен **Bases** — no-code табличный вид базы данных, работает и на мобильном | ⚠️ частично — через `dataviewjs`/Templater (JS в песочнице плагина) | ✅ | ✅ (официальные iOS/Android) |
| **TiddlyWiki** (уже лежит в этом репозитории: `vendor/tiddlywiki/`, сейчас пустой экспорт) | ⚠️ не совсем — весь вики в одном HTML-файле, но каждая «карточка» (**tiddler**) — по сути markdown-подобный текст + произвольные **поля** (ровно как ваша почасовая ставка) | ✅ именно так и задуман — «tiddlers» и есть карточки | ✅ **макросы/виджеты** — встроенный мини-язык вычислений внутри самого вики, есть Node.js-сервер-режим | ✅ (просто открыть HTML) | ✅ (браузер) |
| **Trilium Notes** | ⚠️ своя БД, но есть markdown-импорт/экспорт | ✅ «promoted attributes» — структурированные поля, показываются в таблицах | ✅ **прямое исполнение JS-кода прямо в заметке** — самый явный ответ на «исполнять файлы» | ✅ (TypeScript/Electron) | ⚠️ через веб-клиент |
| **Anytype** | ⚠️ своя локальная база, экспорт в markdown | ✅ «Types» и «Relations» — определяете свой тип объекта со своими полями, буквально конструктор схемы в интерфейсе | ❌ нет исполнения кода | ✅ (Electron+Go) | ✅, но по отзывам 2026 года отстаёт от десктопа |

**Вывод:** ни один не покрывает всё идеально сразу, но **Obsidian+Dataview**
и **TiddlyWiki** ближе всего, и TiddlyWiki уже физически лежит в этом
репозитории неиспользуемым — почти нулевая стоимость попробовать его для
пилота №15/16 прямо сейчас, без нового кода.

## Моя архитектурная рекомендация для собственного приложения

Если делать своё, а не брать готовое — вот архитектура, прямое развитие
пилотов №15 («один источник → N представлений») и №16 (`care-unit.schema.json`)
из этой же папки.

### 1. Формат хранения — Markdown + YAML frontmatter, один файл на «карточку»

```markdown
---
id: haushalt-assistenz
type: service                    # ссылка на схему ниже
category: household
hourly_rate_min: 20
hourly_rate_max: 55
legal_refs: ["§§ 36, 45a SGB XI", "§§ 78, 113 SGB IX"]
updated: 2026-09-06
---

# Помощь по хозяйству

Обычный markdown-текст документа — то, что уже пишется в `soz30` — идёт
здесь без изменений.
```

Это объединяет то, что в пилоте №15 было двумя файлами (`*.source.json` +
markdown-текст) — **в один**. Так делают Obsidian/Logseq/Jekyll/Hugo — это
устоявшийся, не наш придуманный формат («frontmatter»), а значит вокруг него
уже есть готовые парсеры на любом языке.

### 2. Схема — JSON Schema на тип карточки (буквально пилот №16, только на «сервисы»)

Один файл-схема на каждый `type` (service, legal-citation, cost-item,
glossary-term...), проверяющий frontmatter — то же самое, что уже сделано и
проверено в `care-unit.schema.json`. Приложение при сохранении карточки
валидирует её frontmatter по схеме её типа — как `validate.py` из пилота №16,
только встроенное в приложение, а не запускаемое вручную.

### 3. Индекс — SQLite, всегда пересобираемый, никогда не редактируемый руками

Файлы `.md` — источник истины (как уже сделано в `soz30` и в
`sites/pomosch-po-domu`). При старте приложение сканирует папку, парсит
frontmatter всех карточек и строит/обновляет **SQLite**-индекс: одна таблица
на `type`, столбцы — поля из frontmatter (`hourly_rate_min`, `legal_refs`
как JSON-массив и т.д.). Это даёт мгновенные запросы («покажи все услуги
дороже 30 €/час», «найди все карточки, ссылающиеся на § 45a SGB XI») без
парсинга сотен файлов на каждый клик — тот же принцип, что `database.json`
в `sites/pomosch-po-domu`, только не JSON-файл, а настоящая БД с индексами.
Важно: SQLite-файл — **артефакт, не хранится в git**, всегда можно стереть
и пересобрать из `.md`, как `generated/` в пилоте №15.

### 4. Слой «исполнения» — с песочницей, не голый `eval`

Раз документы юридические/финансовые — небезопасно просто выполнять
произвольный код из файла. Два уровня, оба встречаются в реальных продуктах
выше:

- **Блоки-вычисления внутри карточки** (как макросы TiddlyWiki или code-notes
  Trilium) — например, блок ` ```calc `, который приложение считает
  само, в собственном ограниченном языке (сумма `cost_items`, генерация
  Mermaid-диаграммы шагов — то, что сейчас делает `generate_views.py` из
  пилота №15 офлайн, здесь считалось бы прямо при открытии карточки).
- **Плагины** (как у Obsidian) — отдельные, самостоятельно устанавливаемые
  расширения с более широкими правами, но не включённые по умолчанию —
  ядро приложения никогда не исполняет непроверенный код автоматически.

### 5. Алгоритмы сравнения документов — два разных, для двух разных задач

- **Структурированные поля** (почасовая ставка, диапазон стоимости,
  параграфы) — это просто SQL `WHERE`/`JOIN` по индексу из шага 3, без
  всякого ИИ — самая дешёвая и надёжная часть.
- **Сравнение длинного текста двух документов между собой** (например, чем
  реально отличается Widerspruch по одному случаю от другого) — два уровня:
  - **Построчный diff** (алгоритм Майерса — то же, что `git diff`/`diff`) —
    находит точные текстовые различия, дёшево и детерминированно.
  - **Смысловое сходство через эмбеддинги** — каждый абзац превращается в
    вектор, косинусное сходство между векторами находит **похожие по смыслу,
    но по-разному сформулированные** абзацы — это то, что реально помогло бы
    найти повторяющиеся риск-менеджмент-разделы среди 19+ папок `soz30` и
    свести их к общему алгоритму (та самая идея «обобщения в повторяющиеся
    алгоритмы» из самого первого вопроса этой серии).

### 6. Приложение для десктопа и мобильного из одной кодовой базы

Учитывая, что весь остальной код в `games-monorepo` — ванильные
HTML/CSS/JS без сборки, логичное продолжение того же стиля:

| Слой | Технология | Почему |
|---|---|---|
| UI | тот же ванильный HTML/CSS/JS, что и в остальном репозитории (`pult-nuzhd-demo.html` и т.п.) | Один код для всех платформ ниже, без нового фреймворка |
| Десктоп-обёртка | **Tauri** (Rust + системный WebView) | Легче Electron (не тащит Chromium целиком), даёт доступ к файловой системе и SQLite напрямую из Rust |
| Мобильная обёртка | **Capacitor** | Тот же веб-код, нативный доступ к файлам на iOS/Android, минимум переделок |
| БД | SQLite (через `rusqlite` в Tauri или `@capacitor-community/sqlite` в мобильной обёртке) | Один и тот же формат файла на всех платформах |
| Синхронизация между устройствами | Git (десктоп, файлы всё равно markdown) **или** Syncthing/CouchDB-репликация (если нужен мобильный без Git) | Открытый вопрос архитектуры — оба варианта совместимы с «файлы — источник истины» |

## Как это соотносится с уже сделанным в этой папке

Это не новая идея с нуля — это прямое укрупнение того, что уже проверено:

- **Пилот №15** уже показал: один структурированный источник → N
  представлений. Здесь тот же принцип, только источник — не отдельный JSON,
  а frontmatter внутри самого markdown-файла, а «представления» строятся не
  офлайн-скриптом, а живым индексом в приложении.
- **Пилот №16** уже показал: формальная JSON Schema + валидатор на чистом
  stdlib. Здесь та же схема становится схемой типа карточки в приложении.
- **`sites/pomosch-po-domu`** уже показал: markdown — источник истины,
  `database.json`/CSV — производные, не редактируемые руками. Здесь то же
  самое, просто вместо статического JSON — живой SQLite-индекс.

Если хотите, следующий конкретный шаг — маленький рабочий прототип (например,
Python-скрипт, который сканирует папку с `.md`+frontmatter-карточками пилота
№15 и строит из них SQLite-индекс с парой примеров запросов), прежде чем
вкладываться в Tauri/Capacitor-обёртку.
