# API платформы: биллинг, usage-tracking, seat provisioning

[⌂ Вики](../../../README.md) · [Позиции](../../README.md) · [Платформа](../README.md) · API платформы: биллинг, usage-tracking, seat provisioning

## Источник (дословно)

> Develop platform API infrastructure including usage-based tracking, billing integrations, seat provisioning

## Что это простыми словами

Это «коммерческий каркас» платформы — та часть, что превращает технические возможности в продукт, которым можно пользоваться и за который можно платить. Три вещи здесь работают вместе. **Учёт потребления** (usage tracking) считает, кто сколько израсходовал — например, вычислений или вызовов моделей. **Биллинг** (billing) переводит этот учёт в счета и интегрируется с системами оплаты. **Выдача мест** (seat provisioning) заводит и настраивает доступ для сотрудников организации — сколько людей (или агентов) может работать и с какими правами. Всё это выставляется наружу через API-инфраструктуру платформы — единый программный интерфейс, через который к системе обращаются и внешние клиенты, и внутренние сервисы.

## Что конкретно делает инженер

- Строит API-инфраструктуру платформы (platform API): согласованные, версионируемые (versioned) программные интерфейсы, через которые доступны возможности продукта; аутентификация запросов, лимиты частоты (rate limiting), квоты.
- Реализует учёт потребления по факту использования (usage-based tracking): надёжный сбор событий (metering), их агрегация и атрибуция к нужной организации/пользователю/агенту — с требованиями к точности и отсутствию потерь.
- Делает интеграции с биллингом (billing integrations): связка учёта потребления с провайдерами тарификации/платежей, тарифные планы, инвойсинг, обработка перерасхода и лимитов.
- Реализует выдачу мест (seat provisioning): создание и настройку доступов для членов организации, привязку мест к правам (совместно с [идентификацией](identity-systems.md)), масштабирование числа мест.
- Обеспечивает наблюдаемость и корректность биллинг-данных: сверки (reconciliation), идемпотентность (idempotency) при повторах, аудитопригодность расчётов.

## Зачем это Mirendil

Это слой, который делает платформу *продаваемой и многопользовательской*, а не только технически работающей. *Аналитическая реконструкция:* обещание «демократизировать фронтир-R&D» и дать доменным учёным ставить эксперименты через «vibe research» подразумевает внешних платящих клиентов — а значит, нужны учёт потребления, тарификация и управление местами. Учёт потребления особенно важен ещё и потому, что фронтир-нагрузки дороги: без точного metering нельзя ни справедливо распределять дорогие GPU-ресурсы между арендаторами, ни выставлять за них корректные счета. Косвенно эта задача — сигнал зрелости замысла: компания на момент анонса не имеет публичного продукта и выручки, но роль прямо предполагает построение коммерческого каркаса под будущий продукт.

## Термины

- **Usage-based tracking (учёт по потреблению)** — измерение фактического расхода ресурсов субъектом для тарификации и квотирования.
- **Metering** — сбор и агрегация событий потребления с гарантиями точности и без потерь.
- **Seat provisioning (выдача мест)** — заведение и настройка пользовательских доступов («мест») внутри организации.
- **Rate limiting (лимитирование частоты)** — ограничение числа запросов к API за интервал времени.
- **Идемпотентность (idempotency)** — свойство операции давать один и тот же результат при повторном выполнении (важно для биллинга при ретраях).
