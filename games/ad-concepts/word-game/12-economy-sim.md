# 12 — Приложение: симулятор экономики

Навигация: [← Алгоритмы контента](11-algorithms.md) | [README](README.md)

Статус: спецификация офлайн-инструмента (Node/TypeScript-скрипт, вне клиентского бандла). Назначение — проверять и калибровать экономику [05](05-economy.md) ДО того, как номиналы уйдут в remote config (строится в Проходе Б вместе с метой и экономикой, гейт перед Проходом В; в CI — пункт «экономика-симуляция» из процессов [10](10-production.md) §7). Все номиналы симулятор читает из единого конфига — точной копии таблиц [05](05-economy.md) §2 и [06](06-monetization.md) §3/§5; собственных «магических чисел» в коде симуляции нет.

Инварианты уровня документа:

- **INV-S1 (номиналы не мои):** цены, награды и капы — только из конфига-зеркала [05](05-economy.md)/[06](06-monetization.md). Симулятор калибрует **поведенческую модель игрока**, но никогда — номиналы (§8.1).
- **INV-S2 (детерминизм):** прогон воспроизводим из сида: PRNG — mulberry32, сид игрока = `fnv1a32('wordgrove:econsim:v1:{runId}:{playerId}')` — та же схема, что у генератора уровней ([11](11-algorithms.md) §1).
- **INV-S3 (баланс и капы):** монеты не уходят в минус — каждый sink гейтится проверкой баланса, как в продукте; копилка ≤ 200 (переполнение сгорает), заморозки ≤ 3, стаки подсказок ≤ 99, RV-капы из [06](06-monetization.md) §3.1.
- **INV-S4 (таблица-твин):** REF-режим (§5.1) воспроизводит колонку «заработано» таблицы [05](05-economy.md) §4 точно, колонку «потрачено» — в допуске ±10% (§8.2).
- **INV-S5 (первичность книги):** при расхождении первичны [05](05-economy.md)/[06](06-monetization.md)/[09](09-analytics-kpi.md); приложение обновляется синхронно.

---

## 1. Границы модели: что симулируем и что нет

Симулятор не переигрывает словесное ядро — решаемость и solve-time уровней проверяет контент-QA ([11](11-algorithms.md) §5). Здесь уровень — агрегатное событие с исходами «застрял/не застрял», «блестящий/нет».

| Слой | Как моделируется | Источник правды |
|------|------------------|-----------------|
| Прохождение уровней | Скорость из расписания уровней/день + solve-time коридоры баккетов | [05](05-economy.md) §4, [11](11-algorithms.md) §5.2 |
| Застревания и подсказки | P(застревания) по баккету × беглость → лестница спасений (перемешать → RV-1 → платная подсказка) | [03](03-core-gameplay.md) §3, [05](05-economy.md) §2.1 |
| Монеты, жёлуди, стрик, заморозки | Полная транзакционная модель, до монеты | [05](05-economy.md) §1–3 |
| Rewarded-решения | Склонности принятия по сегментам, капы и триггеры из [06](06-monetization.md) §3.1 | [06](06-monetization.md) §3 |
| Interstitial и баннер | Не моделируются — не трогают монетную экономику | — |
| IAP и подписка | В базовом прогоне отсутствуют (таблица [05](05-economy.md) §4 — медианный не-платящий); сценарные инъекции — §6 | [06](06-monetization.md) §5 |
| Ретеншен | Только в COHORT-режиме: R(t) = 0,42 · t^(−0,435) ([09](09-analytics-kpi.md) §4.2) | [09](09-analytics-kpi.md) §4 |

Осознанное следствие: сложность и застревания — входы (из коридоров 03/11), а не эмерджентный выход. Симулятор отвечает на вопрос «что происходит с монетами при заданной кривой сложности», а не «правильно ли генератор держит кривую» (это ответственность [11](11-algorithms.md) §5.3).

**Главный вопрос к симулятору:** держится ли окно конверсии D15–D30 (первое «дно» баланса ~D27–D29, [05](05-economy.md) §4) при полных rewarded-потоках — и насколько его размывают копилка, RV-2 и weekly-миссии (§7, метрика M-12).

## 2. Модель игрока: сегменты беглость × вовлечённость

### 2.1 Сетка сегментов и доли популяции

|  | DAILY (казуал) | CORE | POWER | Σ |
|--|--|--|--|--|
| **STRUGGLER** | 8% | 15% | 2% | 25% |
| **MEDIAN** | 12% | **30%** | 8% | 50% |
| **FLUENT** | 5% | 15% | 5% | 25% |
| **Σ** | 25% | 60% | 15% | 100% |

Контрольные точки (проверяются assert'ом при загрузке конфига):

- Ячейка **MEDIAN × CORE (30%)** — «медианный не-платящий игрок» таблицы [05](05-economy.md) §4. Калибровка §8 ведётся именно по ней.
- Взвешенные сессии/день: `0,25·1,2 + 0,60·2,5 + 0,15·3,5 = 2,3` — внутри коридора «2–3 сессии/день» ([03](03-core-gameplay.md) §4).
- Медиана уровней/день на D15+: 6 (ячейка CORE) — ровно допущение [05](05-economy.md) §4; среднее ≈ 6,9 (хвост POWER), что объясняет, почему средние метрики экономики выше медианных.
- Сегмент DAILY воспроизводит риск «казуал, играющий только daily» ([05](05-economy.md) §5): earn ~100–160/день при почти нулевых тратах — проверка M-10.
- Сегмент POWER воспроизводит «пауэр-игрок 20+ уровней/день, earn 500+/день» ([05](05-economy.md) §5) — проверка M-11.

### 2.2 Параметры беглости (skill)

```ts
type FluencyTier = 'STRUGGLER' | 'MEDIAN' | 'FLUENT';

type FluencyParams = {
  stuckMult: number;       // множитель P(застревания): 1.5 / 1.0 / 0.55
  solveMult: number;       // множитель к p50 solve-time баккета (11 §5.2): 1.35 / 1.0 / 0.75
  bonusPerLevel: number;   // найденных бонус-слов за уровень: 1.5 / 3.0 / 5.0 (жёлуди ×2, 05 §2.2)
  brilliantShare: number;  // доля «блестящих» проходов: 0.15 / 0.40 / 0.65
};
// MEDIAN: 20 + 0.40 × 5 = 22 монеты/уровень — ровно «средний доход/уровень 22» из 05 §4.
```

Базовая вероятность застревания за уровень по баккету (до множителя беглости):

```ts
const P_STUCK: Record<Bucket, number> = { 1: 0.05, 2: 0.10, 3: 0.18, 4: 0.28, 5: 0.45 };
const PEAK_MULT = 1.6;   // каждый 10-й уровень — пик (03 §6.2), спрос на Ракету (05 §7 п.1)
```

Стартовые значения; первичная оценка — с плейтестов Прохода А, затем с телеметрии `hint_use`/`shuffle_use` ([09](09-analytics-kpi.md) §1.1).

### 2.3 Параметры вовлечённости (frequency)

```ts
type EngagementTier = 'DAILY' | 'CORE' | 'POWER';

type EngagementParams = {
  levelsPerDay: (d: number) => number;

  sessionsPerDay: number;  // 1.2 / 2.5 / 3.5

  weeklyP: number;         // выполняемость weekly-миссий: 0.05 / 0.25 / 0.80 (только MC-режим, см. §5)

```

### 2.4 Поведенческие склонности (rewarded, траты)

```ts
type Propensity = {
  // Склонности принятия rewarded НА событие-триггер (стартовые, MEDIAN×CORE):
  rvAccept: {
    rv1: number;  // 0.30 на глубокое застревание (120 c / 5 невалидных, 03 §3); капы: 1/уровень, ≤4/день
    rv2: number;  // 0.08 на экран победы (удвоить монеты уровня, с ур. 5)
    rv3: number;  // 0.55 после daily (повторный спин колеса), 1/день
    rv5: number;  // 0.85 на копилку ≥ 150/200 (06 §3.1)
    rv6: number;  // 0.50 на серию спасения стрика (3 показа, ≤ 1 серии/нед)
    rv7: number;  // 0.40 на ×2 прогресса ивента (2/день в дни ивента)
  };
  // Калибровка §8.3 сводит ВЗВЕШЕННЫЕ показы/DAU к колонке 06 §3.1
  // (0.30 / 0.55 / 0.20 / 0.35 / 0.03 / 0.02; сумма без RV-4 ≈ 1.45 из 1.50).
  // RV-4 (архив daily, 0.05 показа/DAU) не моделируется — не влияет на монеты.

  hintLadder: {
    shuffleResolveP: number;   // 0.60 — застревание снято бесплатным «перемешать» (03 §2.2)
    lampP: number;             // 0.55 — купить Лампу (100), если RV-1 недоступен/отклонён и balance ≥ 100
    scopeP: number;            // 0.18 — Прицел (150) при точечном тупике «осталось 1 слово»
    rocketPeakP: number;       // 0.35 — Ракета (350) на пиковом уровне при balance ≥ 350
  };
  spendStress: (d: number) => number;
  // множитель интенсивности трат: 0.35 (D1–3) → 1.0 (D14) → ~1.4 (D20+), форма — §8.3 шаг 1;
  // отражает «траты нарастают по мере роста сложности» (05 §4) и пики каждого 10-го уровня
  wheelSpin3P: number;         // 0.10/день — импульсный 3-й спин за 200 при balance > 500 (05 §2.1)
  freezeBuyP: number;          // 0.40 — купить заморозку (500) при стрике ≥ 7 под угрозой (05 §7 п.3)
  eventCatchupP: number;       // 0.10/день в ивент-неделю — догон дня за 300 (05 §2.1)
};
```

Лестница спасения при застревании — порядок как в продукте ([03](03-core-gameplay.md) §3): перемешать (бесплатно) → бесплатная Лампа за RV-1 → платная подсказка → «дожать» (solve-time ×2, малый шанс выхода из уровня). Бесплатная подсветка «осталось 1 слово, 180 сек» (1/уровень) моделируется как снижение `scopeP` на 40% — она гасит часть точечных тупиков.

## 4. Псевдокод симуляции 30 дней

```ts
function simulateRun(cfg: SimConfig): RunReport {
  const players = spawnPopulation(cfg);                 // N × сетка §2.1, сиды по INV-S2
  for (const p of players)
    for (let d = 1; d <= 30; d++) simulateDay(p, d, cfg);
  return aggregate(players);                            // метрики §7
}

function simulateDay(p: Player, d: number, cfg: SimConfig): void {
  if (roll(p.rng, p.eng.skipDayP)) { handleMissedDay(p, d); return; }   // стрик под угрозой
  p.log.dayStart(d, p.coins);

  // --- 1. Daily-кроссворд и колесо (с D2) ---
  if (d >= 2 && roll(p.rng, p.eng.doesDailyP)) {
    earn(p, EARN.daily, 'daily');
    p.streak++; grantStreakMilestone(p);                // 3/7/14/30 → 50/120/250/600
    earn(p, wheelPrize(p.rng), 'wheel');                // спин 1, EV 60
    if (cfg.mode !== 'REF' && roll(p.rng, p.prop.rvAccept.rv3))
      { show(p, 'RV-3'); earn(p, wheelPrize(p.rng), 'wheel_rv3'); }
    if (cfg.mode !== 'REF' && roll(p.rng, p.prop.wheelSpin3P) && p.coins > 500)
      { spend(p, PRICES.wheelSpin3, 'wheel_spin3'); earn(p, wheelPrize(p.rng), 'wheel_spin3'); }
  }

  // --- 2. Daily-миссии (с D3; открытие на ур. 12 — 05 §4) ---
  if (d >= 3) for (let m = 0; m < EARN.dailyMissions.count; m++)
    if (roll(p.rng, p.eng.missionP))
      earn(p, randInt(p.rng, 30, 60), 'mission_daily'); // EV дня ≈ 120 × missionP = 84 у CORE

  // --- 3. Уровни атласа ---
  const n = p.eng.levelsPerDay(d);
  for (let i = 0; i < n; i++) {
    const lvl = nextLevel(p);                           // номер → баккет по кривой 03 §6.2 (11 §3.8)
    playLevel(p, lvl, cfg);
  }

  // --- 4. Копилка жёлудей (05 §2.2, RV-5) ---
  if (cfg.mode !== 'REF' && p.piggy >= EARN.piggyOpenAt && roll(p.rng, p.prop.rvAccept.rv5))
    { show(p, 'RV-5'); earn(p, p.piggy, 'piggy'); p.piggy = 0; }        // конвертация 1:1

  // --- 5. Weekly-миссии и ивенты (только MC/COHORT; в REF исключены — прим. 05 §4) ---
  if (cfg.mode !== 'REF') {
    if (d % 7 === 0 && roll(p.rng, p.eng.weeklyP)) earn(p, EARN.weeklyNominal, 'mission_weekly');
    if (isEventWeek(d, cfg) && roll(p.rng, p.prop.eventCatchupP) && p.coins >= PRICES.eventCatchup)
      spend(p, PRICES.eventCatchup, 'event_catchup');
    if (isEventWeek(d, cfg)) earn(p, dailyShare(EARN.eventWeekEV, p.rng), 'event');
  }

  // --- 6. Давление пейволла (окно конверсии, 06 §5.1: «пустой баланс D15+») ---
  if (d >= 15 && p.coins < 300 && !p.firstPressureDay) p.firstPressureDay = d;   // «дно» 05 §4
  p.log.dayEnd(d, p.coins);
}

function playLevel(p: Player, lvl: LevelRef, cfg: SimConfig): void {
  const stress = p.prop.spendStress(p.day);
  let stuck = roll(p.rng, P_STUCK[lvl.bucket] * p.flu.stuckMult * (lvl.isPeak ? PEAK_MULT : 1) * stress);
  if (stuck && roll(p.rng, p.prop.hintLadder.shuffleResolveP)) stuck = false;    // «перемешать»
  if (stuck && cfg.mode !== 'REF' && rv1Available(p) && roll(p.rng, p.prop.rvAccept.rv1))
    { show(p, 'RV-1'); useFreeLamp(p); stuck = false; }                          // бесплатная Лампа
  if (stuck) stuck = !tryPaidHints(p, lvl);            // Лампа → Прицел → Ракета (гейты баланса, INV-S3)
  if (stuck && roll(p.rng, 0.06)) { p.log.quit(lvl); return; }                   // редкий выход из уровня

  const brilliant = !p.hintsUsedThisLevel && roll(p.rng, p.flu.brilliantShare);
  earn(p, EARN.levelBase + (brilliant ? EARN.brilliantBonus : 0), 'level');
  if (cfg.mode !== 'REF' && roll(p.rng, p.prop.rvAccept.rv2))
    { show(p, 'RV-2'); earn(p, lastLevelReward(p), 'level_rv2'); }               // удвоить монеты
  addAcorns(p, Math.round(p.flu.bonusPerLevel) * EARN.acornPerBonusWord);        // кап 200, лишнее сгорает
}

function tryPaidHints(p: Player, lvl: LevelRef): boolean {
  const s = p.prop.spendStress(p.day);
  if (lvl.isPeak && p.coins >= PRICES.rocket && roll(p.rng, p.prop.hintLadder.rocketPeakP * s))
    return buy(p, 'rocket');                            // главный монетный сток пиков (05 §7 п.1)
  if (p.coins >= PRICES.lamp && roll(p.rng, p.prop.hintLadder.lampP * s))
    return buy(p, 'lamp');
  if (p.coins >= PRICES.scope && roll(p.rng, p.prop.hintLadder.scopeP * s * 0.6))
    return buy(p, 'scope');                             // ×0.6 — часть тупиков гасит бесплатная подсветка
  if (p.coins < PRICES.lamp) p.log.softPaywall(p.day);  // «3 выхода, никогда тупик» (03 §3)
  return false;
}

function handleMissedDay(p: Player, d: number): void {
  if (p.streak >= 7) {                                  // горячая точка (05 §7 п.3)
    if (p.freezes > 0) { p.freezes--; return; }
    if (roll(p.rng, p.prop.rvAccept.rv6)) { show3(p, 'RV-6'); return; }          // серия из 3 показов
    if (p.coins >= PRICES.streakFreeze && roll(p.rng, p.prop.freezeBuyP))
      { spend(p, PRICES.streakFreeze, 'freeze'); return; }
  }
  p.streak = 0;
}
```

## 5. Режимы прогона

| Режим | Что включено | Назначение |
|-------|--------------|------------|
| **REF** («таблица-твин») | Детерминированный EV-прогон одной ячейки MEDIAN×CORE, survivor (без пропусков дней). Источники — ровно допущения [05](05-economy.md) §4: уровни, daily, спин 1 колеса, daily-миссии ×0,7, вехи стрика, старт 300. Без weekly, ивентов, копилки и всех RV-доходов | Регресс-тест самого симулятора против таблицы §4 (INV-S4); гейт в CI |
| **MC** (Монте-Карло) | N = 10 000 игроков × сетка §2.1, все потоки §4, survivor | Распределения балансов, окно конверсии, чувствительности |
| **COHORT** | MC × ретеншен R(t) = 0,42 · t^(−0,435) ([09](09-analytics-kpi.md) §4.2): доля когорты, доживающая до дня t | DAU-нормированные метрики: rewarded показы/DAU против [06](06-monetization.md) §3.1 |

REF-декомпозиция earn по дням обязана совпасть с [05](05-economy.md) §4 аналитически (не фитом):

```
D1:  12 ур. × 22                     = 264   (+300 старта → 564)
D2:  9 × 22 + 40 + 60                = 298
D3:  9 × 22 + 40 + 60 + 120 × 0.7    = 382
D4–7:  8 × 22 + 40 + 60 + 84         = 360   (D7 + веха 120 → 480)
D8–14: 7 × 22 + 40 + 60 + 84         = 338   (D14 + веха 250 → 588)
D15–30: 6 × 22 + 40 + 60 + 84        = 316   (D30 + веха 600 → 916)
```

Эти шесть строк — assert-фикстуры REF-режима. Расхождение хоть на монету — красная сборка.

Решение — по фактической телеметрии soft launch, симулятор даёт карту чувствительностей до неё.

## 8. Калибровка против таблицы баланса [05](05-economy.md) §4

### 8.1 Свободные параметры (только поведенческие — INV-S1)

`P_STUCK` по баккетам, `hintLadder`-склонности, `rvAccept`, `brilliantShare`, `bonusPerLevel`, форма `spendStress(d)`, `skipDayP`. Номиналы из §3 не трогаются никогда; если таблица не сводится без правки номиналов — это находка для ГД-экономиста, а не повод «подкрутить» конфиг (эскалация в ревью [05](05-economy.md)).

### 8.2 Целевые функции и допуски

| Гейт | Условие | Жёсткость |
|------|---------|-----------|
| T-1 | REF: earn/день = фикстурам §5 точно | Красная сборка |
| T-2 | REF: траты/день в ±10% колонки [05](05-economy.md) §4; баланс конца дня ±8%; D30 = 676 ± 60 | Красная сборка |
| T-3 | MC: медиана первого «дна» ∈ [26, 30] | Красная сборка |
| T-4 | MC: M-5 в допусках | Красная сборка |
| T-5 | COHORT: M-6 в допусках (±20% на плейсмент) | Жёлтый флаг → ревью склонностей |
| T-6 | MC: M-9 (коридор 400–900) | Жёлтый флаг → отчёт M-12 обязателен |

### 8.3 Процедура (поэтапный покоординатный спуск, фиксированные сиды)

1. **`spendStress(d)`** фитится в REF по колонке трат [05](05-economy.md) §4: сетка узлов D3/D7/D14/D21/D30, монотонная кусочно-линейная интерполяция; минимизируется max-отклонение трат/день. Ожидаемый результат: 0,35 → 1,0 (D14) → ~1,4 (D20+) — рост трат при частотах §2.1 как базе D14.
2. **`hintLadder` + `P_STUCK`** фитятся в MC (MEDIAN×CORE) по M-5 при замороженном stress.
3. **`rvAccept`** фитится в COHORT по M-6 (веса сегментов §2.1 фиксированы).
4. Полный MC-прогон → проверка T-3/T-6 → отчёт §9. Один цикл 1–4; если T-3 падает после шага 3 — расхождение документируется (это и есть ответ M-12), цикл не зацикливается на подгонку.

Анти-переобучение: калибруем по D1–D30, контрольная валидация — прогон до D45 (окно S1: второе «дно» должно существовать, иначе экономика «замкнулась» и IAP-полке нечего продавать после первой покупки).

## 9. Интерфейс запуска и отчёт

```
econsim run --mode=ref|mc|cohort --days=30 --n=10000 --seed=<runId> [--scenario=s1..s5] [--out=report.md]
econsim calibrate --stage=1..4 --fixtures=05-table.json
econsim diff --a=run1.json --b=run2.json      # сравнение прогонов (например, S3 против базы)
```

Выход: `report.md` (таблица M-1…M-12 против целей, графики баланса ASCII/SVG) + `run.json` (полные распределения). В CI на каждый merge — REF-режим (T-1/T-2, < 10 сек); ночной прогон — MC + COHORT (~2 мин на 10 тыс. игроков × 30 дней). Регресс-гейт перед Проходом В: все T-гейты зелёные на актуальном конфиге номиналов.

Границы применимости: симулятор не предсказывает конверсию в платёж (нет модели платёжного намерения) — он локализует **где и когда** возникает дефицит и офферное давление; конверсию меряет только телеметрия ([09](09-analytics-kpi.md) §2, воронка «Первая покупка»).
