# Block Surge — прототип (Проходы А + Б + В + Г)

Играбельное ядро по [главе 03](../03-core-gameplay.md) и [приложению 11](../11-algorithms.md), слой экономики и мета-прогрессии по [главе 04](../04-meta-progression.md) и [главе 05](../05-economy.md), симуляция монетизации и аналитический дашборд по [главе 06](../06-monetization.md) и [главе 09](../09-analytics-kpi.md), плюс soft-launch cockpit (детерминированный симулятор экономики по [приложению 12](../12-economy-sim.md), A/B-фреймворк, панель тюнинга и гейты go/iterate/kill по [главе 09](../09-analytics-kpi.md) §5.4 и [главе 10](../10-production.md)). Без сборщиков и без внешних зависимостей — чистый Canvas 2D + DOM; симулятор работает и в браузере, и как `node sim.js`.

## Запуск

Любой статический сервер из каталога `games/ad-concepts`:

```
python -m http.server 8145 --bind 127.0.0.1 --directory games/ad-concepts
```

Открыть http://127.0.0.1:8145/block-puzzle/prototype/ (в проекте есть конфиг `.claude/launch.json` с этим сервером). Файл `index.html` работает и напрямую с `file://`.

## Управление

Перетаскивай фигуру из дока на поле 8×8: зелёный призрак — можно ставить, красный — нельзя, подсвечиваются линии, которые соберутся. Заполняй ряды и столбцы; серии очисток дают комбо ×2/×3/×5 и заряжают шкалу «Прилив». При полной шкале в четвёртое гнездо дока приходит кристальная бомба 3×3 — перетащи её на поле. Game over — когда ни одна фигура не помещается.

## Объём Прохода А

Реализовано: поле 8×8, bag-генератор с режиссёром сложности и проверкой размещаемости (SOLVENCY-CHECK), drag&drop мышью и тачем, одновременная очистка рядов/столбцов, счёт по таблице 03 §2.2, комбо-автомат, шкала «Прилив» и бомба, честный game over, рекорд в localStorage (`blocksurge_best`).

В проде стек меняется на TypeScript + Phaser 3 + Capacitor (см. [главу 10](../10-production.md)).

## Объём Прохода Б — экономика и мета-прогрессия

Слои добавлены поверх ядра, не переписывая core loop. Новый код — в отдельных модулях `economy.js` и `meta.js`, подключённых в `index.html` **перед** `game.js`; ядро вызывает их через несколько добавленных хук-функций (`window.Meta.onMove/onBomb/onGameEnd/onNewGame/snapshot`). Константы экономики (валюта, earn-rate, цены бустеров) вынесены в `ECON` наверху `economy.js` и согласованы с главой 05.

**Экономика монет (05 §1–2, §4).** Единственная валюта — монеты. Приход: за очистку линии `1 × множитель комбо` (05 §2.1), бонус за «чистое поле», и монеты за конец партии `floor(score/100)` (аналог «Победа на уровне 25–50»). Баланс — в HUD (верхняя панель) и в `localStorage`; стартовый баланс 200 (FTUE-подарок, 05 §3).

**Бустеры-инвентарь (05 §2.2, §5).** Три бустера с именами и ценами из главы 05: **Отмена** (80🪙, откат последнего хода), **Обмен** (120🪙, новая тройка фигур), **Молот** (150🪙, убрать одну клетку поля). Кнопки со счётчиком — в UI партии под полем; расходуются при использовании, докупаются за монеты (клик по пустому бустеру покупает, повторный — применяет). Влияние на партию — через глобалы ядра (`board`/`hand`/`dealHand`/`refreshPlaceable`).

**Карта «Путешествия» (04 §2).** Линейный трек из 12 узлов; прогресс — по суммарным ★ за партии (1/2/3★ по очкам). Узлы дают награды (монеты/бустеры), «босс»-узлы — усиленные. Открывается кнопкой «🗺️ Карта · магазин · миссии» с основного экрана.

**Стрик дней (04 §3).** Цикл 7 дней с нарастающей наградой (30→150🪙, день 7 + Молот). Для прототипа — кнопка «Получить награду дня» (доступна раз в календарный день) и «⏭ Новый день (тест)» для имитации смены суток; пропуск 2+ дней сбрасывает серию.

**Ежедневные миссии (04 §4.1).** 3 миссии в день с ротацией из пула (детерминированно по дате). Прогресс считается по событиям партии (очистки линий, комбо, «чистое поле», сыгранные партии, очки); все 3 закрыты → бонус-сундук 60🪙.

Мета-экран (карта + магазин бустеров + миссии + стрик) достижим из игры и обратно. Петля замкнута: партия → монеты/звёзды/прогресс миссий → мета → бустеры → влияют на партию.

Лёгкий трекер `window.Analytics` логирует ключевые события по дереву [09 §2.2](../09-analytics-kpi.md) (`currency_earn/spend`, `booster_used`, `mission_complete`, `streak_change`, `game_end`).

### Хранение и совместимость сейва

Проход А хранил один ключ `blocksurge_best` (рекорд, не тронут). Проход Б добавляет ключ `blocksurge_meta` (единый JSON: монеты, бустеры, ★, карта, стрик, миссии). Проход В добавляет ОТДЕЛЬНЫЙ ключ `blocksurge_monetize` (remove-ads/подписка, гео, дневные капы рекламы, lifetime-выручка/показы). Схема совместима: при отсутствии ключа или отдельных полей подставляются дефолты (глубокое слияние + санитизация), поэтому старые сейвы игру не ломают (проверено: сейв только с `blocksurge_best=4200` грузится без ошибок — рекорд сохраняется, мета и монетизация инициализируются дефолтами со стартовым балансом 200, гео «бленд», реклама включена).

## Объём Прохода В — монетизация и аналитический дашборд

> ⚠️  **ВСЁ — СИМУЛЯЦИЯ.** Никаких реальных рекламных SDK/сетей и платежей. «Показ рекламы» = экранный оверлей-заглушка с отсчётом 3–5 сек (в проде тут AppLovin MAX / AdMob, [06](../06-monetization.md) §8). «Покупка» = мгновенная выдача товара без денег. Слово «СИМУЛЯЦИЯ» стоит в шапке `monetize.js` и на всех рекламных/магазинных экранах.

Новый код — в отдельных модулях `monetize.js` (реклама + IAP) и `analytics.js` (дашборд), подключённых в `index.html` **после** `economy.js` и **перед** `game.js`. Ядро (`game.js`) и мету (`meta.js`) не переписывает — только добавляет монетизацию через глобалы ядра (`newGame`/`board`/`dealHand`/`gameOver`/…) и наблюдение за экранами. Конфиг eCPM/прайсов/капов — в объекте `MON` наверху `monetize.js`, числа из главы 06.

**Реклама-заглушки (06 §2–3).**
- **Interstitial (INT-2)** между партиями: перехват клика «Играть заново» на экране итога (capture-фаза, опережает `newGame` ядра). Капы зашиты кодом ([06](../06-monetization.md) §3): не в FTUE (сыграно < 2 партий / первые 30 сек сессии — прокси «5 уровней / 8 мин»), ≥90 сек между показами, частотный кап (≥1 партия между), ≥60 сек после rewarded, не после IAP в сессии, ≤10/день, отключается Remove Ads/подпиской. Недопоказы логируются событием `ad_capped` с причиной и видны в дашборде.
- **4 rewarded-плейсмента (06 §2.2):** **RW-1** «Второй шанс» (экран game over — освобождает 2 строки + 2 столбца и продолжает ту же партию, 1/партию); **RW-2** «×2 монеты за партию» (экран game over, 3/день); **RW-3** «Бесплатный бустер» (Молот, в мете, 2/день); **RW-4** «×2 награда дня» (+100🪙, в мете, 2/день). Каждый по клику показывает оверлей-симуляцию (5 сек → «Забрать награду»), выдаёт награду и генерирует rewarded-выручку.
- **Banner (BAN-1, 06 §2.3):** фиксированная полоса снизу с меткой «СИМУЛЯЦИЯ», авто-рефреш (прототип 15 сек, прод 30) = 1 показ; скрывается при Remove Ads/подписке; считает показы только на игровом экране.

**eCPM-модель (06 §4).** Показ → выручка = `eCPM(формат×гео) × jitter(±25%) / 1000`. Бенчмарки: rewarded $16 (US) / $13 (бленд) / $6.4 (Tier-2/3 = ×0.4), interstitial $14 / $10 / $5.6, banner $0.5 / $0.4 / $0.2. Гео-переключатель Tier-1 / Бленд 60/40 / Tier-2/3 — в дашборде, влияет на eCPM будущих показов.

**Полка IAP (06 §5).** 11 SKU: Remove Ads ($4.99), наборы монет ($0.99–$99.99), Копилка, бандлы бустеров, Season Pass, Мега-сундук, Подписка Surge Premium ($7.99/мес — no-ads + 200🪙/день). Клик = симуляция покупки: выдаёт товар (монеты/бустеры/флаги remove-ads/подписки/скина), логирует revenue по прайсу. Remove Ads и подписка реально прячут INT + баннер (rewarded остаётся).

**Аналитический дашборд (09).** Живые KPI сессии (сессия = 1 симулированный DAU за день) против целей главы 09: показы по форматам vs impressions/DAU (INT 7.0 / RW 1.8 / BAN 35), ad ARPDAU vs $0.105, IAP-выручка (с пометкой «плательщик ≠ среднее DAU»), blended vs $0.15, доля Ad/IAP (цель 70/30), воронка rewarded (shown/accepted), текущие eCPM vs целями, недопоказы interstitial. Каждое событие сессии перерисовывает дашборд. Считается по РЕАЛЬНЫМ событиям сессии.

## Объём Прохода Г — soft-launch cockpit (симулятор + A/B + тюнинг + гейты)

> Кокпит — **офлайн-инструмент прод-команды**, а не часть игры. Он не трогает ядро/экономику/монетизацию/сейв игры: читает симулятор и хранит свои настройки в отдельном ключе `localStorage` (`blocksurge_softlaunch`). Открывается кнопкой 🚀 в верхней панели.

Новый код — в двух модулях `sim.js` (симулятор экономики по приложению 12) и `experiments.js` (A/B + панель тюнинга + гейты), подключённых в `index.html` **после** `analytics.js` и **перед** `game.js`. Числа — из приложения 12 (§2 сегменты, §3 номиналы) и главы 05 (§4 кривая).

### Симулятор экономики `sim.js` (приложение 12)

Моделирует **N виртуальных игроков** сегментов скилл×частота (сетка 12 §2.1: NOVICE/BASE/SKILLED × LIGHT/CORE/HEAVY, доли Σ=1.00) × **30 дней**. Партия — агрегатная move-цепь (12 §4.1): автоматы комбо (множитель ×2/×3/×5) и Прилива (заряд 10×mult, шкала 100, кристалл — очки, не монеты, 11 §5). Полная транзакционная модель монет sources/sinks (05 §2): линии, победы уровней + 3★ + босс ×2, колесо, стрик-ramp 30→150, миссии, недельный бандл, сундуки; sinks — бустеры (инвентарь → покупка = sink), continue №1/№2, билет Поля, восстановление стрика, скины. Capы rewarded RW-1..4 (06 §2.2), pity (11 §3.5), **INV-E4** (sink гейтится проверкой баланса, отказ → `denied`).

**Детерминизм (INV-E2):** собственный seeded-RNG (mulberry32), сид игрока = `fnv1a32('blocksurge:econsim:v1:{runId}:{playerId}')` — та же схема, что в ядре/мете. **Никаких** `Math.random`/`Date.now` в расчётах — `runId` приходит параметром. Проверено: повторный прогон с тем же `runId` даёт бит-в-бит один результат.

**Два способа запуска (тот же код):**
- **Браузер** — кнопка «▶ Прогнать симуляцию» в кокпите; кап N=100–400 игроков, прогон <1 c; результат рендерится таблицей.
- **Node** — `node sim.js` печатает текстовую сводку в stdout (`module.exports` + запуск при `require.main === module`; `node sim.js [runId] [N]`). Совместимость обеспечена UMD-обёрткой (`window.Sim` в браузере, `module.exports` в node).

**Вывод:** медиана баланса BASE×CORE по дням vs таблица 05 §4 (отклонение в %), точки дефицита (M8 `<200`, M9 `<400`, M10 накопители `>5000`), earn/spend ratio (M2), ad-ARPDAU, доля sinks, fail-коридоры по сегментам (M3), здоровье Прилива (M7), красные флаги дизайна (12 §8.4).

**Калибровка (12 §8.2).** Свободные EV (миссии, недельный бандл, novelty, наклон stress, спрос на бустеры — это **поведенческая модель**, §8.3, НЕ номиналы) подобраны покоординатным спуском в `econ-sim.baseline` (`BOOK_TUNE` в `sim.js`). Результат `node sim.js` (N=2000, SURVIVOR): **D1 ≈ −3%, D7 ≈ +13%, D8 ≈ +10%, D14 ≈ −5%** — ранняя неделя, пик (D8) и равновесие (D14) трекают таблицу 05 §4 в пределах ~10–13%; earn/spend ratio 0.97 (коридор 0.95–1.15 ✓); Прилив M7 = 74% (≥60% ✓); все fail-коридоры в норме (03 §5.2); накопители 0.1% (M10 ≤3% ✓); красных флагов нет. Отклонения **D21–D30** (−25% на D21/D25, плато ~370 против идеализированного «100» таблицы) — задокументированный эффект **аффордабилити-пола (INV-E4)**: медиана упирается в цену continue/бустера (150–200) и не доходит до нуля, пока приход её пополняет. Это не баг симулятора, а именно та дефицитная динамика, что открывает окно IAP (M8 `<200` = 28%, M9 `<400` = 42% к D30). Номиналы (цены, награды, капы) симулятор **не тюнит** (INV-E1).

### A/B-фреймворк + панель тюнинга `experiments.js`

**A/B (09 §6).** Пул из 3 экспериментов: **INT-кап 7 vs 5/день**, **RW-2 множитель ×2 vs ×3**, **стартовый баланс 200 vs 300**. Назначение варианта — **детерминировано** по `fnv1a32(sessionId + ':' + expId) % nVariants`: одна сессия всегда получает те же варианты. `sessionId` — стабильный per-install id в `localStorage`. Варианты видны в шапке кокпита (`A/B: int_cap=B, rw2_mult=B, …`) и в блоке A/B. Кнопка «⚖ Сравнить A/B» гоняет **оба** варианта (свой `runId` на вариант → детерминированно) и показывает дельту первичной метрики (ad-ARPDAU/ratio/баланс/дефицит). Тумблер «применять назначенные варианты к прогону» (по умолчанию **off**, чтобы главная таблица валидировала чистый baseline против 05 §4).

**Панель тюнинга.** Ручки, редактируемые слайдером/числом: `W_HARD` (сложность hard-сегмента 21–60), ad-капы (INT/DAU, Banner/DAU, RW-2 cap), `COIN_*` earn-rate (миссии EV, недельный бандл, спрос на бустеры, RW-2 множитель, стартовый грант), eCPM (rw/int/banner, 06 §4). Правки сохраняются в `localStorage`, подсвечиваются, применяются к симулятору (проверено: `W_HARD=1.3` поднимает fail hard-сегмента 16.6%→19.8%) и **сбрасываются «к значениям книги»** (по одной ручке или все сразу). Номиналы 05/06 (цены, награды, капы rewarded) в панели отсутствуют — это решения глав (INV-E1).

**Гейты go / iterate / kill (09 §5.4, 10 P7).** По симулированной COHORT-когорте (метрики на DAU) + сценарий удержания (пессимист/база/оптимист, 09 §5.2). Четыре метрики против kill/scale-порогов: **D1** (kill<30/scale≥38), **D7** (<9/≥15), **ad-ARPDAU T1-когорт** (<$0.06/≥$0.10), **D7 ROAS** = LT7 × (ad-ARPDAU симулятора + IAP-ARPDAU) / CPI (<20%/≥40%). Вердикт: любая метрика в kill → **KILL**; все в scale → **GO/SCALE**; иначе (+ красные флаги симулятора) → **ITERATE** с жёстким лимитом **≤2 iterate-цикла** (10 P7), дальше — решение kill/scale на данных. Проверено: база (D1 38/D7 15, CPI $0.90) → **GO/SCALE** (LT7 2.66 = 09 §5.1, ROAS 53%); пессимист (D1 32/D7 11, CPI $1.10) → **ITERATE** (D1/D7/ROAS в серой зоне).
