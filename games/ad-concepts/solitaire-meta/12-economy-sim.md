# 12. Приложение Б — Симулятор экономики: модель игрока, 30 дней, стыковка с балансом

**Проект:** Orchard Peaks. Назад: [11-algorithms.md](11-algorithms.md)

Приложение — исполняемая проверка главы [05-economy.md](05-economy.md): агентная симуляция 30 дней жизни медианного неплатящего игрока. Симулятор читает выход генератора уровней напрямую ([11-algorithms.md](11-algorithms.md) п. 11.9) и отвечает на три вопроса: (1) происходит ли плановый переход профицит→дефицит с первым монетизационным решением в окне дня 12–16 ([05] пп. 5.4, 5.7); (2) держатся ли коридоры контрольного дашборда ([05] п. 5.8); (3) насколько экономика чувствительна к смещению WR, темпа взноса и rewarded-поведения. Все номиналы берутся из таблиц [05] п. 5.2 и [06-monetization.md](06-monetization.md) п. 6.2 — в симуляторе нет ни одной локальной константы баланса.

## 12.1. Архитектура и режимы

```
генератор батча ([11] п. 11.6) ──► SerializedLevel[] ──┐
                                                        ├──► симулятор ──► отчёт + CI-гейты приёмки
номиналы и кривые (главы 03/05/06) ──► EconomyParams ───┘
```

| Режим | Исход партии | Когда используется |
|---|---|---|
| **Трассировочный** | жадные прогоны реальных раскладов батча (`greedyRollouts`, [11] п. 11.8) — тот же код, что в валидации Q4 | приёмка контентного батча: экономика меряется на тех самых уровнях, что уйдут в билд |
| **Аналитический** | розыгрыш Бернулли по эффективной кривой W(n) ([03-core-gameplay.md](03-core-gameplay.md) п. 3.5) | быстрые итерации баланса и сценарии чувствительности (п. 12.7) |

Режимы обязаны сходиться: |WR_trace − WR_analytic| ≤ 2 п.п. по каждой полосе уровней таблицы 11.7 — это тест стыковки генератора и экономики, входит в приёмку батча ([11] п. 11.9). Все числа ниже — аналитический режим, 2 000 агентов, сиды `1000 + 7·i` (инвариант I-E1).

```typescript
  missionsDaily:  { count: 3; range: [150, 400];  minAttempts: 4 };    // [04] п. 4.4
  missionsWeekly: { count: 3; range: [800, 1500] };
  streak7: [200, 300, 400, 500, 600, 800, 1500];                       // [04] п. 4.4
```

**Инварианты симулятора:**

| # | Инвариант |
|---|---|
| I-E1 | Детерминизм: прогон воспроизводим по сиду бит-в-бит (тот же PRNG-контракт, что I6 в [11]) |
| I-E2 | Нет двойного учёта WR: эффекты бустеров/спасений на победу уже входят в W(n); поверх кривой идут только деньги (п. 12.2) |
| I-E3 | Банкротство не терминально: при балансе < E(n) день игры заканчивается, но стрик/колесо/миссии следующего дня и RW6 всегда возвращают в игру (п. 12.8) |
| I-E4 | Капы rewarded применяются до начисления: RW6 ≤ 3/день, RW1 ≤ 1/уровень, RW3 ≤ 2/день ([06] п. 6.2) |
| I-E5 | Инвентарь бустеров ≤ 9 шт. каждого ([05] п. 5.5); покупка при полном стаке невозможна |

## 12.2. Модель игрока 45–70

**Ключевое решение — эффективный WR.** Кривая W(n) из [03] п. 3.5 — это *целевой наблюдаемый* винрейт реального игрока: конверсия спасений (+35 п.п. в момент тупика, [05] п. 5.6), анти-чёрн-баффы и типовое применение бустеров уже «внутри» неё — именно её увидит событие `level_finish` ([09-analytics-kpi.md](09-analytics-kpi.md) п. 9.1). Поэтому симулятор разыгрывает исход по W(n) + скилловый сдвиг, а спасения и бустеры моделирует **только как денежные потоки** с частотами их применения. Добавка их ΔWR поверх кривой была бы двойным учётом (инвариант I-E2) — ранние версии модели именно на этом давали ложный профицит +80 тыс. монет к D30.

| Параметр персоны | Распределение | Обоснование |
|---|---|---|
| Скилловый сдвиг WR | N(0, 4 п.п.), клип ±8 п.п. | разброс узкий: единственный скилловый рычаг — серия ([03] п. 3.2); ЦА гомогенна ([01-concept.md](01-concept.md)) |
| Попыток в день | таблица A(t): 14 → 12 → 11 → 10 (дни 4–7) → 9 → 8 (день 21+), ×N(1, 0.12) | 2.6 сессии/день, 8–11 уровней/день на D7 ([03] п. 3.8; [09] п. 9.4) |
| День адопции rewarded | Triangular(10, 14, 21) | «без rewarded до дня 10», рутина к дню 21 ([05] п. 5.4) |
| Склонность тратить `aff` | U(0.85, 1.15) | множитель к частотам покупок; узкий — персона «медианный неплатящий» |
| Агрессия трат `aggro(t)` | 0.35 (дни 1–2) → 0.55 (3–5) → 1.05 (6–10) → 1.8 (11+) | дни 1–4 «обучение богатством», привычка к бустерам растёт ([05] п. 5.4) |
| Порог «богатства» | 8·E (дни 1–5) → 6·E → 4·E (день 11+) | спонтанные покупки бустеров только выше порога |
| Гейт трат после адопции | 3·E → 1.5·E | с RW6-подстраховкой игрок тратится «до дна» — механика карусели ([05] п. 5.5) |

```typescript
interface PlayerProfile {
  skillOffset: number;        // −0.08..+0.08 к W(n)
  attemptsMult: number;       // 0.7..1.3
  rwAdoptDay: number;         // 10..21; Infinity в сценарии no-rewarded
  spendAffinity: number;      // 0.85..1.15
}

interface PlayerState {
  coins: number; harvest: number; level: number;     // level = n, монотонно растёт по победам
  lossStreakOnLevel: number;                         // для анти-чёрн-пити ([03] п. 3.5)
  freeUndoLeft: number;                              // стартовые 2 ([05] п. 5.3)
  zone: number; orderIdx: number;                    // прогресс сада (п. 12.4)
  boosterStock: Record<'joker'|'plus5'|'basket', number>; // ≤ 9 (I-E5)
}
```

**Поведенческие политики** (все вероятности умножаются на `aff` и `aggro(t)`, капы — по [06] п. 6.2):

```typescript
// «Кошелёк» RW6: оффер показывается при coins < 2·E ([06]); берётся при реальной нужде
function policyWallet(st: PlayerState, t: number, e: number, viewsToday: number): boolean {
  return t >= profile.rwAdoptDay && st.coins < e && viewsToday < P.rw.walletCapDay
      && rng() < 0.75;                        // show rate 70–80% при высокой нужде ([06] п. 6.2)
}
// Спасение в тупике: сперва RW1 (бесплатно), затем монеты 0.9·E; повтор 1.2·E ([03] п. 3.6)
function policyRescue(st, t, e): 'RW1' | 'PAY' | 'DECLINE' {
  if (t >= profile.rwAdoptDay && rng() < 0.60) return 'RW1';        // 55–65% оффер→просмотр
  const gate = t >= profile.rwAdoptDay ? 1.5 : 3.0;                 // «до дна» после адопции
  if (st.coins > gate * e && rng() < min(0.9, 0.65 * aff * aggro(t))) return 'PAY';
  return 'DECLINE';
}
// Pre-level бустер: на «камнях» (n mod 10 = 0) — RW3 бесплатно или «+5 карт» за 900;
// вне камней — спонтанная покупка выше порога богатства (джокер/+5/лукошко поровну)
```

## 12.3. Псевдокод: 30 дней монетного контура

```typescript
function simulateDay(st: PlayerState, t: number, profile: PlayerProfile, day: DayLog): void {
  const stone = (n: number) => n % 10 === 0 && n >= 10;
  earn(st, P.streak7[(t - 1) % 7], day);                    // «Утренняя лейка», без пропусков дней
  if (rng() < 0.9) earn(st, P.wheelEV, day);                // колесо ярмарки, 1/день

  const A = round(attemptsBase(t) * profile.attemptsMult);
  for (let i = 0; i < A; i++) {
    const n = st.level, e = E(n);
    while (policyWallet(st, t, e, day.rw6Views)) {          // RW6: добор монет до входа
      grantRW(st, round(0.8 * e), day); day.rw6Views++;
    }
    if (st.coins < e) break;                                // банкротство дня — инвариант I-E3
    pay(st, e, day);                                        // взнос ([05] п. 5.2)

    const buy = policyBooster(st, t, e, stone(n));          // денежный поток, WR не трогаем (I-E2)
    if (buy) pay(st, P.boosters[buy.kind], day);
    if (st.freeUndoLeft > 0) st.freeUndoLeft--;             // стартовые ундо гасят первые платные
    else if (rng() < 0.12 * aggro(t)) pay(st, P.boosters.undoPaid, day);

    const pity = st.lossStreakOnLevel >= 5 ? 0.09           // «лёгкая рука» ([03] п. 3.5)
               : st.lossStreakOnLevel >= 3 ? 0.05 : 0;      // сток +2 — скрытый бафф
    const p = clamp(W(n) + profile.skillOffset + pity, 0.02, 0.995);
    const win = rng() < p;                                  // трассировочный режим: greedyRollout(level)

    if (rng() < (1 - p) * 0.9) {                            // тупик со столом ≥ 60% — оффер спасения
      const r = policyRescue(st, t, e);
      if (r === 'PAY') { pay(st, round(0.9 * e), day);      // конверсия уже в W(n) — только деньги
        if (st.coins > 2 * e && rng() < 0.30) pay(st, round(1.2 * e), day); } // повторное спасение
    }

    if (win) {
      let gain = round(M(n) * e)                            // выигрыш W(n) = M(n)·E(n)
               + P.stockBonusPerCard * chapterOf(n) * sample(P.stockLeftOnWin); // бонус стока
      if (t >= profile.rwAdoptDay && rng() < 0.08) {        // RW2 «удвоить» — редкая привычка персоны
        day.rwIncome += round(M(n) * e); gain += round(M(n) * e);
      }
      earn(st, gain, day);
      st.harvest += harvestYield(n, buy, t);                // п. 12.4
      day.wins++; st.level++; st.lossStreakOnLevel = 0;
    } else {
      st.harvest += round(harvestYield(n, buy, t) * U(0.45, 0.65)); // пол поражения ≥ 50% ([11] Q4)
      st.lossStreakOnLevel++;
    }
  }

  if (day.attempts >= P.missionsDaily.minAttempts)          // daily-миссии закрываются игрой
    for (let m = 0; m < 3; m++) if (rng() < 0.85) earn(st, round10(U(150, 400)), day);
  if (t % 7 === 0)                                          // weekly-миссии
    for (let m = 0; m < 3; m++) if (rng() < 0.80) earn(st, round10(U(800, 1500)), day);
  for (const [need, reward] of P.chestTiers)                // сундук тёти Марты
    if (day.wins >= need) earn(st, reward, day);

  settleGardenOrders(st, t, day);                           // п. 12.4
  day.close(st);                                            // снапшот: баланс, E(level), sink/source
}
```

Функции `earn`/`pay`/`grantRW` пишут в раздельные счётчики `sources`, `sinks`, `rwIncome` — отношение sink/source считается и с rewarded-грантами, и без них (нужно для находки Ф1, п. 12.6). IAP не моделируется: персона — неплатящий; конверсия и выручка — предмет сценариев [09] п. 9.5, которым этот симулятор поставляет `дефицит·E(n)` как входной параметр спроса.

## 12.4. Симулятор сада

Урожайная разметка приходит из генератора: номинал уровня — 10–14 урожая с учётом мешков ([04-meta-progression.md](04-meta-progression.md) п. 4.2, [11] п. 11.8). Коэффициент реализации — следствие квот Q1/Q4 из [11] п. 11.8: победа отдаёт 100% разметки, поражение — медианно 55% (розыгрыш U(0.45, 0.65)); на плато при WR 55% фактический приток ≈ 0.55·1.0 + 0.45·0.55 ≈ **0.80 номинала** (в [11] заложено ≈ 0.77 при поле ровно 50% — симулятор чуть щедрее за счёт распределения выше пола).

```typescript
function harvestYield(n: number, buy: Purchase | null, t: number): number {
  let h = U_int(10, 14);                                   // номинал уровня, мешки внутри ([04] п. 4.2)
  if (buy?.kind === 'basket' || rw3BasketActive) h *= 2;   // золотое лукошко / RW3 ([06] п. 6.2)
  if (P.goldenBedDays.includes(t)) h *= 2;                 // ивент «Золотая грядка» ([04] п. 4.7)
  return h;
}

function settleGardenOrders(st: PlayerState, t: number, day: DayLog): void {
  while (true) {
    const cost = ORDER_COST[zoneKind(st.zone)][st.orderIdx];
    if (cost === undefined) { st.zone++; st.orderIdx = 0; day.zoneClosed = st.zone; continue; }
    if (st.harvest < cost) break;
    st.harvest -= cost; st.orderIdx++; day.orders++;       // заказ → визуальный прогресс + альманах
  }
}
```

**Стоимости заказов** — калибровочный выход симулятора (диапазон заказа 40–400 и «зона ≈ 20 уровней ≈ 2–3 дня активной игры» — [04] п. 4.2):

| Зона | Заказов | Стоимости | Итого | Роль |
|---|---|---|---|---|
| 1 «Крыльцо» | 8 | 40…160 | **750** | FTUE-исключение ниже общего диапазона — аналогично уровням 1–5 вне формулы сложности ([11] п. 11.7): иначе гейт «зона 1 к D7» ([04] п. 4.9) недостижим |
| 2 «Клумбы» | 10 | 40…220 | **1 300** | разгон к общему диапазону |
| 3+ | 12 | 40…200 | **1 440** | нижняя треть диапазона 1 400–2 200 ([04] п. 4.2); верхняя половина диапазона — только с зоны 5+ и при живых ивентовых множителях |

Проверяемые нормативы: медиана «заказов в день» ≥ 1 (правило темпа [04] п. 4.2; KPI «≥ 1.2 заказа на DAU» [04] п. 4.9 включает и платящих/подписчиков с +50% урожая); зона 1 закрыта к D7 у ≥ 60% когорты ([04] п. 4.9). Результаты — п. 12.6.

## 12.6. Валидация против главы 05: профицит → дефицит

**Находки (вход в тюнинг remote config до soft launch):**

- **Ф1 — определение метрики RW6.** При равновесии карусели RW6-видео ≈ 0.4–0.9/день — это согласуется с картой плейсментов [06] п. 6.2 (4.0 rewarded-показа/DAU × доля RW6 13/68 ≈ 0.76 видео), но строка дашборда [05] п. 5.8 «RW6-показов 1.8–2.6» достижима только как показы *оффера* (`ad_offer_shown`: баннер кошелька на карте сада виден многократно), не видео. Требуется зафиксировать определение в [09] п. 9.1, иначе тревога дашборда будет ложной.
- **Ф2 — высота карусели.** Равновесный баланс к D30 ≈ 3–3.5·E (в дни недельных миссий — до 5·E) вместо 1–2·E таблицы 5.4. Причина структурная: приходы вне ядра (миссии + стрик + колесо + сундук ≈ 1·E/день) при sink/source ≤ 1.15 не дают опуститься ниже. Толкать траты сильнее нельзя — вылетают К5/К6 (см. сценарий RW2 в п. 12.7). Рычаги, не ломающие коридоры: номиналы миссий −15–20% на D14+ (персонализация через E(n) уже предусмотрена [05] п. 5.5) или порог оффера RW6 с 2·E до 1.5·E. Решение — A/B в soft launch; на LTV-сценарии [09] п. 9.5 сдвиг не влияет (спрос точки №1 [05] п. 5.7 сохраняется, день 12).
- **Ф3 — темп прогрессии.** n(30) ≈ 149 против 196 в таблице 5.4: таблица неявно предполагала эффективный WR выше целевой кривой [03] п. 3.5. Следствие положительное: 240 уровней хватает на ~48 дней вместо 38 — запас контента к global ([10-production.md](10-production.md)) больше планового; следствие для экономики — E(n) на D30 равен 2 070, а не 3 800, что и объясняет часть Ф2.
- **Ф4 — сад.** Гейт «зона 1 к D7 у 60%» держится только при FTUE-стоимости зоны 1 ≈ 750 (п. 12.4). Тоталы зон 3+ в первом месяце обязаны сидеть у нижней границы диапазона (≈ 1 450): при 1 800+ медиана заказов падает до 0.6/день и правило темпа [04] п. 4.2 ломается уже на D10.

## 12.7. Чувствительность

Каждый сценарий — то же население, один изменённый параметр. Точка «Кошелька» — медиана; баланс D30 — во взносах E(n(30)).

| Сценарий | Кошелёк | D30, ·E | n(30) | Sink/Source D14+ | Вывод |
|---|---|---|---|---|---|
| **База** | 12 | 3.1 | 149 | 1.09 | — |

Главный вывод — подтверждение тезиса [11] п. 11.7: **калибровка WR — это калибровка экономики.** Смещение фактического WR на ±3 п.п. двигает точку «Кошелька» на ∓1 день, баланс D30 на ±20% и просмотры RW6 на ∓30% — поэтому допуск приёмки батча по WR симуляторов жёстче допуска по D ([11] п. 11.9), а кривая E(n) и WR не тюнятся одновременно (эффекты вырождены: 1.012→1.014 ≈ −3 п.п. WR; A/B-тесты разносить по времени, [09] п. 9.6).

## 12.8. Пограничные случаи и тесты приёмки

**Пограничные случаи:**

- **Банкротство в нуле.** Баланс < E(n), rewarded не адоптирован: день заканчивается (I-E3), наутро стрик + колесо + миссии дают 550–1 500 монет; на плато (E ≈ 2 000) возврат к игре занимает до 2 дней без RW6 и 0 дней с ним. Тест: в базовом прогоне доля агентов с ≥ 2 днями подряд без единой партии = 0; в сценарии no-rewarded — предмет мониторинга чёрна, не гейт.
- **Двойной учёт WR** (I-E2). Регресс-тест: прогон с принудительным `ΔWR(бустер) > 0` поверх кривой обязан упасть — контрольная сборка сравнивает EV_core(20/100/камень) с эталонами +227 / +5 / −310 из [11] п. 11.7 (допуск ±10%).
- **Сходимость режимов.** Трассировочный прогон батча против аналитического: |WR| ≤ 2 п.п. по полосе. Расхождение больше — брак батча (генератор), не экономики: сначала проверяется `avgChainLen` → M(n) ± 0.15 ([11] пп. 11.5, 11.9).
- **Капы rewarded.** RW6 ровно 3/день даже при балансе 0 (I-E4); грант 0.8·E не индексируется ивентовыми множителями ([05] п. 5.5). Тест: суточный rewarded-доход ≤ 2.4·E + RW2-даблы ≤ 0.6·E.
- **Стартовые запасы.** 2 бесплатных ундо и джокер из [05] п. 5.3 гасят первые платные применения (< 500 монет эффекта) — на контрольные точки не влияют, но обязаны присутствовать: их отсутствие смещает сальдо дня 1 на −3%.
- **Переполнение инвентаря** (I-E5): покупка при 9 шт. блокируется политикой — как в клиенте, cap из [05] п. 5.5.

**Тесты приёмки экономического прогона (CI, вместе с батчем контента [11] п. 11.9):**

| Тест | Критерий |
|---|---|
| Контрольные точки К1–К8 | все ✓, кроме явно зарегистрированных находок с тикетами |
| Детерминизм | повторный прогон по сиду идентичен бит-в-бит (I-E1) |
| Эталоны EV_core | +227 / +5 / −310 ± 10% ([11] п. 11.7) |
| Сходимость режимов | \|WR_trace − WR_analytic\| ≤ 2 п.п. по полосам таблицы 11.7 |
| Коэффициент урожая | реализация 0.77–0.82 номинала; медиана сбора в поражениях ≥ 50% ([11] Q4) |
| Чувствительность | сценарии п. 12.7 пересчитываются на каждом изменении номиналов [05]/[06]; выход К5 из коридора в базе — блокер релиза конфига |

После soft launch симулятор переключается с синтетической персоны на фактические распределения (`level_finish`, `economy_balance`, `ad_offer_shown` — [09] п. 9.1): сначала сверка прогноза с когортами (гейт: точка «Кошелька» ± 2 дня), затем — прогон каждого кандидата remote config до выкатки. Цикл замыкается: генератор ([11]) → симулятор (это приложение) → дашборды ([09]) → тюнинг ([05]/[06]) → генератор.
