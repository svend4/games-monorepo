# Единая рендер-абстракция 2D/2.5D/3D

## TL;DR
Одна симуляция мира кормит **три взаимозаменяемых бэкенда рендера** — Canvas2D (v1), изометрию
(v2) и Three.js (v3) — через единый интерфейс `IRenderer`. Симуляция не знает, чем её рисуют;
существующие v1/v2/v3 переосмысляются не как «версии игры», а как **разные окна в один и тот же
мир** ([NX-VIS-001#detali]). Это превращает сегодняшнюю проблему ревью — «движок размазан по трём
клиентам, симуляция переплетена с `THREE`/`ctx`» ([NX-REVIEW#sec2]) — в чистый порт-адаптер контракт.

## Краткое содержание
Ревью зафиксировало ключевой долг: «движок общий» — это миф, модульна только v3, а v1 (3701 стр) и
v2 (369 стр) — независимые монолиты с **0 ссылок на `shared/`** ([NX-REVIEW#sec2]). При этом даже в
`shared/` рендер не отделён от логики: `shared/systems/EnemySystem.js` напрямую зависит от глобалов
`scene`, `MAT`, `THREE`, `pg`, `PS` — то есть **симуляция знает, как её рисуют**. Любая новая
механика приходится трижды: один раз на `ctx.fillRect` (v1), один на изо-проекцию (v2), один на
`THREE.Mesh` (v3). Четвёртый бэкенд (например, WebGPU или текстовый/ASCII-режим) означал бы форк всей
игры.

`NX-SYS-004` вводит **границу между «что в мире» и «как его рисуют»**. Симуляция (ECS из [NX-SYS-001])
ничего не знает о пикселях; она выдаёт **презентационную модель** (что где находится, в каком
состоянии, с какими событиями). Три адаптера — `Canvas2DRenderer`, `IsoRenderer`, `ThreeRenderer` —
реализуют один интерфейс `IRenderer` и переводят эту модель в свой бэкенд. Так три существующих
клиента становятся синхронными окнами в одну симуляцию, а диегетичный UI ([NX-INN-005]) и эхо-маркеры
([NX-INN-003]) описываются **один раз** и проявляются во всех трёх окнах.

## Расширенное содержание (общее)

### Граница: симуляция ↔ презентация ↔ бэкенд
Три слоя с однонаправленной зависимостью (в духе правила слоёв [NX-SYS-001#tri-kontrakta-sloyov]):

```
СИМУЛЯЦИЯ (ECS, системы)        → не знает ни про THREE, ни про ctx, ни про DOM.
   │ производит за кадр
   ▼
ПРЕЗЕНТАЦИОННАЯ МОДЕЛЬ          → «renderables»: список того, что видно, в МИРОВЫХ координатах,
   │ читают адаптеры              + состояние (hp-доля, угроза, диегетичные сигналы NX-INN-005).
   ▼
IRenderer (порт)               → один интерфейс; три реализации (адаптера):
   ├─ Canvas2DRenderer  (v1, top-down 2D, ctx.fillRect/drawImage)
   ├─ IsoRenderer       (v2, изометрия, мир→экран проекция, z-сортировка)
   └─ ThreeRenderer     (v3, WebGL, InstancedMesh/scene graph)
```

Ключевой инвариант: **стрелка только вниз**. Адаптер читает презентационную модель и владеет своими
ресурсами (текстуры/меши/спрайты); симуляция к адаптеру **не обращается никогда**. Это прямое
применение паттерна «порты и адаптеры» (Hexagonal Architecture, Cockburn) к рендеру — см.
«Что нового и кирпичики».

### Презентационная модель как «снимок мира»
Симуляция за кадр отдаёт не команды рисования, а **декларативное описание**: «сущность 42 — гоблин,
позиция (x,z), повёрнут так-то, hp-доля 0.4, флаг „ранен", анимация „атака", вошёл в кадр». Адаптер
сам решает, что это: красный прямоугольник (v1), изо-спрайт с z-сортировкой (v2) или
`InstancedMesh`-инстанс с шейдером раны (v3). Это **retained-mostly** модель: адаптер диффит снимок
кадра с предыдущим и трогает только изменившееся (создал/удалил/подвинул), а не пересоздаёт сцену —
закрывает риск «LOD/geometry каждый кадр» из [NX-REVIEW#sec3-1].

### Зачем это столпам видения
- **«Три клиента — одно окно»** ([NX-VIS-001#detali]): игрок смотрит на тот же мир в 2D с телефона
  и в 3D с ПК. Без общей презентационной модели это невозможно — миры бы разъехались.
- **Диегетичный UI один раз** ([NX-INN-005]): «бюджет диегетичности» (hp как состояние тела, компас
  как артефакт) описывается в презентационной модели как сигналы; каждый адаптер лишь *выражает* их
  в своей эстетике. Сегодня HUD ([shared/ui/HUD.js](../../shared/ui/HUD.js)) — это 8 DOM-оверлеев,
  привязанных к одному клиенту; в модели IRenderer диегетичные сигналы переносимы.
- **Эхо-мир виден везде** ([NX-INN-003]): призраки-«эхо», послания и постройки — это renderables с
  тегом `echo`; они появятся одинаково во всех трёх окнах, потому что приходят из одной симуляции.

## Детали и частные случаи

### Контракт IRenderer (минимальный)
Адаптер реализует жизненный цикл и приём снимка. Никаких «нарисуй прямоугольник» в интерфейсе — только
«вот мир, покажи его по-своему»:

| Метод | Назначение | Заметки |
|-------|-----------|---------|
| `init(canvasEl, opts)` | создать контекст/сцену/камеру | v1/v2 — `getContext('2d')`; v3 — `WebGLRenderer` |
| `resize(w, h, dpr)` | реакция на ресайз/DPR | закрывает пробел адаптивности [NX-REVIEW#sec3-5] |
| `beginFrame(camera)` | начать кадр, применить камеру | камера — в мировых координатах, общая для всех |
| `sync(snapshot)` | принять презентационную модель кадра | диффит с предыдущим снимком (retained) |
| `present(alpha)` | вывести кадр; `alpha` — интерполяция | `alpha` из фикс-timestep GameLoop [NX-SYS-001] |
| `worldToScreen(p)` / `screenToWorld(p)` | проекция для ввода/диегетичных меток | у каждого бэкенда своя; контракт един |
| `dispose()` | освободить ресурсы | защита от утечек при смене окна |

`camera` в мировых координатах — единственный «общий язык» позиционирования. Для v1 это сдвиг/зум
top-down; для v2 — параметры изо-проекции (`tileW/tileH`, угол); для v3 — `PerspectiveCamera`. Метод
`worldToScreen` обязателен, потому что диегетичные метки ([NX-INN-005]) и эхо-маркеры ([NX-INN-003])
позиционируются в мире, но для подсветки/тач-зон нужен экранный пиксель.

### Renderable: единица презентационной модели
Один элемент снимка (поле `kind` определяет, как адаптер его трактует):

```
Renderable {
  id, kind,            // 'enemy' | 'player' | 'npc' | 'loot' | 'fx' | 'echo' | 'tile'
  pos {x,y,z}, rot,    // МИРОВЫЕ координаты (z=высота; для 2D игнорируется)
  prevPos,             // для интерполяции по alpha
  visual: {            // декларативные сигналы, НЕ команды рисования
    sprite|model,      // ассет-ключ; адаптер сам резолвит в текстуру/меш
    tint, scale, anim, // состояние представления
    hpFrac, threat,    // диегетичные сигналы NX-INN-005 (рана/угроза)
    diegetic: {...}     // хромота, дыхание, свечение раны — выражает адаптер
  },
  flags                // bitset: visible, dirty, justEntered, justLeft
}
```

Важно: `visual.hpFrac` и `diegetic.*` — это **намерение**, а не «нарисуй полоску». v1 может показать
HP мелкой цифрой, v2 — цветом спрайта, v3 — шейдером и анимацией скелета. Так «бюджет диегетичности»
из [NX-INN-005] кодируется один раз и переводится тремя адаптерами.

### Граничные случаи и асимметрии бэкендов
- **2.5D не равно 3D.** Изометрия (v2) — это 2D-рисование с **z-сортировкой по `y+z`** и проекцией
  мир→экран; у неё нет настоящей глубины. Контракт это допускает: `IsoRenderer.sync` сортирует
  renderables, `ThreeRenderer` отдаёт сортировку GPU. Симуляция различий не видит.
- **Что есть в 3D, но нет в 2D** (тени, объём, частицы-в-глубине): презентационная модель описывает
  *эффект* (`fx: dust`), а отсутствующий в 2D вариант адаптер либо упрощает (плоский спрайт), либо
  опускает. Деградация — ответственность адаптера, не симуляции.
- **InstancedMesh только для v3** ([NX-REVIEW#sec3-2]): группировка одинаковых `kind` в инстансы — это
  оптимизация внутри `ThreeRenderer`, скрытая за `sync`. v1/v2 решают батчинг иначе (спрайт-атлас).
- **Текущий долг shared.** `EnemySystem.js` сегодня лезет в `scene.add`/`MAT`/`THREE` напрямую — это и
  есть нарушаемая граница. По NX-SYS-004 система лишь помечает сущность компонентом представления;
  меш создаёт `ThreeRenderer` при `justEntered`. Это совместимо с namespace-`NEXUS.*` из
  [NX-SYS-001#chestnye-globaly].

### Производительность границы
Снимок не должен аллоцировать массив объектов каждый кадр (GC-мусор — отдельный риск [NX-REVIEW#sec3-1]).
Снимок — это **переиспользуемые буферы** (SoA-подобные или пул `Renderable` через `ObjectPool` из
[NX-SYS-001#objectpool]); `sync` читает их по индексу. Дифф — по `dirty/justEntered/justLeft` флагам, а
не полным сравнением. Это сохраняет бюджет кадра 16 мс ([NX-ARCH#sec9]) даже при общей модели.

## Предложения и варианты реализации

Псевдокод-заготовка для второго роя. Сигнатуры и полный реестр `kind`/`anim` — отдельной спекой
(`40-specs/`, зависимый документ).

```pseudo
// ── ПОРТ: интерфейс, который реализует каждый бэкенд ───────────────
interface IRenderer {
  init(canvasEl, opts); resize(w, h, dpr); dispose()
  beginFrame(camera); sync(snapshot); present(alpha)
  worldToScreen(p) -> {sx, sy};  screenToWorld(sx, sy) -> {x, y, z}
}

// ── СИМУЛЯЦИЯ не знает про рендер: строит снимок из ECS ────────────
function buildSnapshot(world, pool):
  snap = pool.frame()                         // переиспользуемый буфер (нет GC)
  for id in world.query(['Transform','Visual']):     // archetype-ECS, NX-SYS-001
    t = world.get(id,'Transform'); v = world.get(id,'Visual')
    r = snap.acquire(id)
    r.pos = t.pos; r.prevPos = t.prevPos; r.rot = t.rot
    r.kind = v.kind; r.visual = v.signals     // hpFrac, threat, diegetic — НАМЕРЕНИЕ
    r.flags = v.flags                          // visible/dirty/justEntered/justLeft
  return snap

// ── КОНТУР КАДРА: одна симуляция → N окон ─────────────────────────
function frame(dt, alpha):
  simulation.fixedUpdate(dt)                   // фикс-timestep, NX-SYS-001/GameLoop
  snap = buildSnapshot(world, snapshotPool)
  for renderer in activeRenderers:             // 1..3 окна одновременно
    renderer.beginFrame(sharedCamera)          // камера в МИРОВЫХ координатах
    renderer.sync(snap)                        // адаптер диффит и трогает изменившееся
    renderer.present(alpha)                     // интерполяция prevPos→pos по alpha

// ── АДАПТЕР v1: Canvas2D (top-down) ───────────────────────────────
Canvas2DRenderer implements IRenderer {
  sync(snap):
    for r in snap where r.flags.visible:
      s = this.worldToScreen(r.pos)            // сдвиг/зум камеры
      drawSprite(ctx, atlas[r.visual.sprite], s, tintByHp(r.visual.hpFrac))
      if r.visual.diegetic.wounded: drawVignette(s)   // рана как намёк, не полоска
}

// ── АДАПТЕР v2: изометрия (2.5D) ──────────────────────────────────
IsoRenderer implements IRenderer {
  worldToScreen(p): return { sx:(p.x-p.z)*tileW/2, sy:(p.x+p.z)*tileH/2 - p.y }
  sync(snap):
    visible = snap.filter(r => r.flags.visible)
    visible.sort(by => by.pos.x + by.pos.z)    // z-сортировка вместо настоящей глубины
    for r in visible: drawIsoSprite(ctx, this.worldToScreen(r.pos), r.visual)
}

// ── АДАПТЕР v3: Three.js (3D, InstancedMesh) ──────────────────────
ThreeRenderer implements IRenderer {
  sync(snap):
    for r in snap:
      if r.flags.justEntered: this.spawnInstance(r)      // меш создаёт АДАПТЕР, не система
      if r.flags.justLeft:    this.recycleInstance(r)
      if r.flags.dirty:       this.updateInstance(r)     // позиция/анимация/рана-шейдер
    this.threeRenderer.render(scene, camera)             // InstancedMesh: 1 draw call/kind
}
```

**Развилки реализации:**
- **A. Push-снимок (рекомендую):** симуляция строит снимок, адаптеры читают. Просто, тестируемо без
  GPU, естественно для «N окон сразу». Минимальный риск.
- **B. Pull-наблюдатели:** адаптер подписан на события ECS (`entity:spawned/moved/died` через EventBus
  [NX-SYS-001]) и ведёт свою сцену сам. Меньше копий, но три подписчика легче рассинхронизировать —
  риск «миры разъехались». Годится, если снимок окажется дорогим.
- **C. Гибрид:** статика зоны (тайлы, постройки) — через события (редко меняется), динамика
  (враги/эхо/fx) — через снимок. Вероятный итог для продакшена; начать с A.

Порядок внедрения (привязка к [NX-STRAT-003] вертикальному срезу): сначала извлечь `IRenderer` и
сделать `ThreeRenderer` поверх уже модульной v3; затем переписать v1 как `Canvas2DRenderer` на той же
симуляции (доказательство «одна симуляция — два окна»); v2 как `IsoRenderer` — третьим.

## Что нового и какие кирпичики
- **НОВОЕ:** не сама идея рендер-абстракции (она стара), а то, что **существующие три клиента
  браузерной RPG (2D/2.5D/3D) превращаются в синхронные окна одной симуляции**, и поверх этого
  «бюджет диегетичности» из [NX-INN-005] кодируется **один раз** как презентационные сигналы, а не
  трижды как разный UI. Связка «асинхронный эхо-мир ([NX-INN-003]) виден идентично во всех трёх
  бэкендах» — редкость: обычно у игры один рендер на всю жизнь.
- **Источники (humanities/c20-proven):** «порты и адаптеры» (Hexagonal Architecture, A. Cockburn,
  2005) и разделение Model/View (MVC, Trygve Reenskaug, Smalltalk-80, 1970-е) — проверенные кирпичики
  изоляции домена от представления.
- **Проверенные кирпичики (геймдев XX–XXI):** retained-vs-immediate scene graph; double buffering;
  z-сортировка изометрии (классика 90-х — Diablo/Civilization); спрайт-атласы; `InstancedMesh`-батчинг
  (уже частично в `shared/engine/ParticleSystem.js` — один `THREE.Points`, [NX-REVIEW#sec1] п.9).
- **Чего мало в других играх:** игра, которую можно открыть **одновременно** в 2D, изометрии и 3D как
  три окна в один персистентный мир, — почти не встречается; обычно «2D-версия» и «3D-ремейк» — это
  разные кодовые базы. Здесь это один контракт `IRenderer`.
- **Связь с полиглот-веткой:** будущий WebGPU/WASM-бэкенд ([NX-POLY-008]) — это ещё один адаптер за
  тем же портом, без изменения симуляции.

## Риски, открытые вопросы
- **Утечка абстракции.** Если в `Renderable` начнут просачиваться 3D-понятия (нормали, материалы),
  2D-адаптеры станут заглушками-обманками. Митигировать ревью-правилом: в презентационной модели —
  только *намерение*, бэкенд-специфика живёт в адаптере.
- **Стоимость снимка.** Полный снимок каждый кадр может стать дорогим при росте мира — отсюда развилка
  B/C (pull/гибрид) и переиспользуемые буферы. Нужен профиль (бюджеты — будущий [NX-SYS-005]).
- **Камера как общий язык.** Перспектива (v3) и ортопроекция (v1/v2) различаются; «одна камера в
  мировых координатах» — упрощение. Открытый вопрос: единый ли FOV/зум или у каждого окна свой,
  синхронизированный лишь по позиции цели.
- **Реальный объём миграции.** v1 (3701 стр) и v2 (369 стр) — монолиты с 0 ссылок на `shared/`
  ([NX-REVIEW#sec2]); переписать их под `IRenderer` — основная работа (effort: L), и её надо оценивать
  отдельно от v3, как и предупреждает [NX-SYS-001#riski].
- **Диегетичность vs читаемость.** Перенос HP «в тело» ([NX-INN-005]) в 2D-окне может ухудшить
  читаемость — нужен a11y-fallback (числовой режим), тоже выражаемый через сигналы.

которой утверждение «три окна в один мир» становится исполнимым. Возражения и развилки — в
`90-comments/`.
