# Подвопросы: полиглот-архитектура (детализация ветви T1)

## TL;DR
Это **рабочее дерево открытых вопросов** по полиглот-архитектуре NEXUS — детализация
корневой ветви **T1** из повестки [NX-RND-001](NX-RND-001-research-agenda.md#T1). Пять
осей: **Q1** границы языков, **Q2** цена interop, **Q3** сборка полиглот-репо, **Q4**
отладка через границы, **Q5** безопасность чужого кода и моддинга. Каждый лист —
*формулировка + гипотеза + как проверить (эксперимент/метрика)*. «Велосипед с
крылышками»: сам приём (research-tree с неизменными id) — проверенный кирпичик
(IETF «Open Issues», ADR), новое измерение — **каждая гипотеза приходит с
фальсифицируемым тестом и числовым порогом**, а не с мнением.

## Краткое содержание
[NX-POLY-001](../50-polyglot/NX-POLY-001-language-per-role.md) отвечает «*какой* язык под
роль», [NX-POLY-003](../50-polyglot/NX-POLY-003-interop.md) — «*как* языки разговаривают».
Оба документа закрывают **что мы решили**, но оставляют хвост **что мы ещё не измерили**:
где именно проходит граница «один процесс / разные процессы», какой codegen-формат даёт
минимум дрейфа, чем собирать PHP+Python+JS+WASM в одном репо, как отлаживать баг,
прыгающий через три языка, и как пускать чужой код (моддинг) в живой мир, не открыв дыру.

Документ превращает эти хвосты в **адресуемое дерево** Q1…Q5 с неизменными id (как везде
в вики — см. [NX-META-001 §6](../00-meta/CONSTITUTION.md)). Каждый узел — это не лозунг,
а **гипотеза с протоколом проверки**: что мерим, на чём, какой порог делает гипотезу
истинной или ложной. Закрытый вопрос не удаляется — получает ссылку на документ-ответ
(POLY/SPEC/SYS). Список метавопросов вынесен в `open_subquestions`.

## Расширенное содержание (общее)

### Зачем отдельное дерево под T1
Повестка [NX-RND-001](NX-RND-001-research-agenda.md) держит **шесть корней** и не уходит
вглубь — иначе она перестаёт быть навигатором. Ветвь T1 (полиглот) — самая «инженерная»
из шести: её подвопросы измеримы (латентность, размер бинаря, время сборки, число CVE),
а значит, их нельзя оставлять на уровне «надо подумать». Этот документ берёт T1 и
**разворачивает в проверяемые гипотезы**, чтобы прикладные POLY-доки закрывали их
экспериментом, а не декларацией.

### Кирпичик и новое измерение
Проверенный кирпичик — **research-tree с id-путями** (issue-backlog, ADR, RFC «Open
Issues»). Наше **крылышко** — дисциплина «каждый узел = фальсифицируемая гипотеза +
протокол проверки + числовой порог». То есть мы не спрашиваем «хорош ли FFI?», а пишем:
*«Гипотеза: FFI окупается, только когда вызовов > N/кадр; проверка — микробенч A против B;
порог — N, ниже которого IPC по латентности неотличим»*. Это переносит на дизайн-вики
приём из инженерии производительности (benchmark-driven decisions) и из науки
(фальсифицируемость по Попперу, `humanities`).

### Обозначения узлов
🔴 открыт и блокирует другие решения; 🟡 открыт, не блокирует; 🟢 в основном закрыт
(есть документ-ответ). «→» — кандидат-владелец (документ, который должен закрыть узел).
Каждый лист содержит три поля: **Ф** (формулировка), **Г** (гипотеза), **П** (как
проверить).

## Детали и частные случаи

### Q1 — Границы языков: где проходит шов между ролями
> Сколько языков, под какие роли, и где граница «новый язык оправдан / лишний».
> Корень: [NX-POLY-001](../50-polyglot/NX-POLY-001-language-per-role.md),
> [NX-POLY-004](../50-polyglot/NX-POLY-004-filetype-language-matrix.md).

- **Q1.1** 🟢 Критерий «язык под роль» как таковой. → [NX-POLY-001](../50-polyglot/NX-POLY-001-language-per-role.md)
- **Q1.2** 🟡 Граница JS ↔ WASM по горячести пути.
  - **Ф:** при какой доле времени кадра, проведённой в функции, её стоит переписать из JS в Rust→WASM?
  - **Г:** перенос окупается, только если функция занимает **> ~15–20 % времени кадра** и вызывается «толсто» (батч), иначе маршалинг через линейную память съедает выигрыш (см. [NX-POLY-003#details](../50-polyglot/NX-POLY-003-interop.md)).
  - **П:** профиль tick-loop (`performance.now()` / DevTools) на эталонной сцене; микробенч «тонкий vs толстый вызов» через WASM-границу; порог — точка, где JS и WASM-вариант равны по wall-clock.
- **Q1.3** 🟡 Граница PHP ↔ Python по «горячести» и старту процесса.
  - **Ф:** при какой частоте вызовов CLI-пайп (старт интерпретатора) проигрывает долгоживущему HTTP-сервису?
  - **Г:** старт CPython стоит десятки мс; при **> ~5–10 вызовов/сек** на эндпоинт CLI-пайп проигрывает HTTP-микросервису (режимы A/B в [NX-POLY-003#детали](../50-polyglot/NX-POLY-003-interop.md)).
  - **П:** замер времени `proc_open(['python', ...])` пустого скрипта (старт) vs `curl` к запущенному Flask; построить кривую «частота → суммарная латентность», найти пересечение.
- **Q1.4** 🟡 Когда оправдан *новый* язык в стеке. → [NX-RND-002](NX-RND-002.md)
  - **Ф:** что должно быть истинно, чтобы добавить Rust/Lua/Perl, а не растянуть существующий язык?
  - **Г:** новый язык оправдан, если выполняется ≥2 из: (a) есть зрелая библиотека, которую дорого портировать; (b) профиль требует нативной/песочничной скорости (WASM); (c) роль концептуально иная (моддинг-DSL, см. Q5.4). Один аргумент — недостаточно.
  - **П:** ретроспективный чек-лист на каждый язык уже в репо (PHP/Python/JS/SQL): прошёл бы он этот фильтр? Гипотетический прогон для Rust (Q1.2) и Lua (Q5.4).
- **Q1.5** 🟡 Полиглот ↔ когнитивная нагрузка: предел числа языков. → [NX-RND-002](NX-RND-002.md)
  - **Ф:** сколько языков рой/команда держит без падения скорости и роста багов на стыках?
  - **Г:** до **4–5 «активных» языков** нагрузка приемлема при условии «узкой талии» (JSON-over-всё, [NX-POLY-003](../50-polyglot/NX-POLY-003-interop.md)); шестой язык окупается, только если он изолирован в одной роли и не участвует в interop напрямую.
  - **П:** считать долю багов «на стыке» (issue-метки) и время онбординга в каждый язык; коррелировать с числом языков по мере роста репо. Метрика — баги-на-стык/месяц.

### Q2 — Цена interop: латентность, маршалинг, дрейф контрактов
> Сколько стоит каждый разговор языков и где платим лишнее.
> Корень: [NX-POLY-003](../50-polyglot/NX-POLY-003-interop.md).

- **Q2.1** 🔴 Граница «один процесс / разные процессы»: критерий FFI→IPC. → [NX-RND-002](NX-RND-002.md), связан с [NX-RND-001#T6.1](NX-RND-001-research-agenda.md#T6)
  - **Ф:** при каком бюджете латентности на вызов выгода FFI (наносекунды) перестаёт оправдывать его риск (краш рушит хост-процесс)?
  - **Г:** если требуемая латентность стыка **> ~1 мс** и вызовов **< ~1000/кадр**, IPC (пайп/HTTP) по совокупной задержке неотличим от FFI, но безопаснее — FFI тогда не нужен.
  - **П:** микробенч: одна и та же «горячая» функция через (a) FFI/WASM, (b) CLI-пайп, (c) localhost-HTTP; таблица «вызовов/кадр → латентность»; порог — где кривые IPC и FFI расходятся заметно для игрока.
- **Q2.2** 🟡 Стоимость сериализации JSON на горячих путях.
  - **Ф:** когда JSON-«узкая талия» становится узким местом и пора на бинарный формат?
  - **Г:** для PHP↔JS на типичных payload'ах (< ~10 КБ) JSON дешевле инфраструктуры бинаря; переход оправдан только на payload'ах **> ~100 КБ** или **> ~1000 сообщений/сек**.
  - **П:** бенч `json_encode`/`JSON.parse` на реальных размерах ответов `nexus_api.php`; сравнить с MessagePack/бинарём; метрика — мс на (де)сериализацию и доля от общего времени запроса.
- **Q2.3** 🟡 Маршалинг сложных структур через WASM-границу.
  - **Ф:** на какой сложности структуры (строки/массивы/вложенность) выигрыш WASM съедается копированием в линейную память?
  - **Г:** скаляры — бесплатно; массивы чисел — дёшево при «толстом» вызове; строки/вложенные объекты — дорого, и при частом обмене ими WASM проигрывает JS.
  - **П:** бенч из [NX-POLY-008](../50-polyglot/NX-POLY-008-wasm-native-perf.md): «толстый vs тонкий вызов» и «скаляр vs массив vs строка» на горячих путях (pathfinding, шум).
- **Q2.4** 🟡 Codegen из единого источника: какой IDL минимизирует дрейф. → [NX-RND-002](NX-RND-002.md), → [NX-SPEC-003](../40-specs/NX-SPEC-003-schema-and-codegen.md)
  - **Ф:** JSON Schema / Protobuf / собственный IDL — что даёт минимум рассинхрона контрактов на 4 целях (TS-типы, PHP-валидатор, SQL DDL, Python-модель)?
  - **Г:** JSON Schema выигрывает для NEXUS: нативен «узкой талии», есть генераторы под все целевые языки, не тянет тяжёлый toolchain Protobuf; ценой — слабее типизация чисел (Q2.6).
  - **П:** прототип одной схемы (`loot_request@v1`) → сгенерить артефакты на всех 4 целях каждым из трёх IDL; сравнить число ручных правок, размер toolchain, время сборки.
- **Q2.5** 🟡 Версионирование контрактов на стыке.
  - **Ф:** какая политика совместимости держит `nexus_api.php` и файлы-контракты живыми при эволюции?
  - **Г:** обязательное поле `schema_version` + правило «только аддитивные изменения внутри мажора» (новые опциональные поля не ломают старых читателей) покрывает 90 % изменений без сломов.
  - **П:** прогон сценариев «старый клиент ↔ новый сервер» и наоборот на наборе изменений схемы; считать долю сломов; см. риск дрейфа в [NX-POLY-003#risks](../50-polyglot/NX-POLY-003-interop.md).
- **Q2.6** 🟡 Числа на границе (f64, BIGINT, деньги).
  - **Ф:** где целые `> 2^53` теряют точность при проходе SQL→PHP→JSON→JS?
  - **Г:** любой `BIGINT`/денежный id, проходящий через JS-`number`, обязан передаваться **строкой**; иначе тихая порча данных.
  - **П:** тест-вектор с id вроде `9007199254740993`: прогнать сквозь весь конвейер, сверить вход и выход побайтно.

### Q3 — Сборка полиглот-репо: как собрать PHP+Python+JS+WASM вместе
> Один репозиторий, четыре toolchain'а — чем дирижировать.
> Корень: [NX-SYS-003](../30-systems/NX-SYS-003-build-and-deploy.md).

- **Q3.1** 🟡 Единый task-runner. → [NX-SYS-003](../30-systems/NX-SYS-003-build-and-deploy.md)
  - **Ф:** Make / just / npm-scripts / собственный Python-runner — чем запускать разнородные шаги (cargo, python, composer, копирование артефактов)?
  - **Г:** `just` или Make как «оркестратор оркестраторов» (тонкие рецепты, делегирующие в нативные тулы) проще, чем тащить всё в npm-scripts; на Windows (XAMPP, см. окружение) `just` переносимее Make.
  - **П:** написать минимальный `justfile`/`Makefile` с целями `build:wasm`, `gen:content`, `db:migrate`, `serve`; замерить, заводится ли «из коробки» на чистой машине Win/Linux.
- **Q3.2** 🟡 Гранулярность и инкрементальность сборки.
  - **Ф:** как не пересобирать WASM при правке только PHP (и наоборот)?
  - **Г:** разделение по артефактам + хеш-зависимости (cargo и так инкрементален; для Python-генерации — отметка `mtime`/хеш входа) убирает лишние пересборки.
  - **П:** замер «холодная vs тёплая» сборка каждого артефакта; цель — правка в одном языке не триггерит сборку другого.
- **Q3.3** 🟡 Воспроизводимость окружения. → [NX-SYS-003](../30-systems/NX-SYS-003-build-and-deploy.md)
  - **Ф:** как зафиксировать XAMPP(PHP) + Python + Rust-toolchain так, чтобы у любого участника роя/команды собиралось одинаково?
  - **Г:** пины версий в манифестах (`composer.json`, `requirements.txt`/`pyproject`, `rust-toolchain.toml`, `package-lock.json`) + один скрипт `bootstrap` дают воспроизводимость без обязательного Docker; Docker — опция для CI.
  - **П:** прогон `bootstrap` на чистой VM Windows и Linux; зафиксировать расхождения версий/поведения; метрика — «сколько ручных шагов до зелёной сборки».
- **Q3.4** 🟡 Где живут сгенерированные артефакты (commit vs build).
  - **Ф:** коммитить `*.wasm` и codegen-выход в git или собирать на месте?
  - **Г:** codegen-контракты (Q2.4) — коммитить (детерминированы, малы, диффятся, нужны без toolchain); `*.wasm` — собирать (бинарно, шумит в diff).
  - **П:** оценить размер/частоту изменения каждого артефакта; правило по типу артефакта, согласованное с [NX-POLY-004](../50-polyglot/NX-POLY-004-filetype-language-matrix.md).

Иллюстрация целей рунера (набросок `justfile`):

```make
# justfile — единый вход в полиглот-сборку NEXUS
wasm:                                  # Rust -> WASM (горячие пути клиента)
    cargo build --target wasm32-unknown-unknown --release
    cp target/wasm32-unknown-unknown/release/grid.wasm games/nexus/shared/engine/

gen:                                   # Python генерирует контент в файлы-контракты
    python tools/gen_content.py --out games/nexus/shared/data

codegen:                               # одна JSON Schema -> типы/валидаторы на все языки
    python tools/codegen.py design/40-specs/schemas --targets ts,php,sql

db:                                    # применить SQL-миграции
    php tools/migrate.php

build: codegen gen wasm                # порядок важен: контракты -> контент -> бинарь
serve: build
    php -S 127.0.0.1:8000 -t games/nexus/v1-2d-mmo
```

### Q4 — Отладка через границы языков
> Баг прыгает JS → HTTP → PHP → пайп → Python → SQL. Где его ловить?
> Белое пятно повестки T1 — этот документ его открывает.

- **Q4.1** 🔴 Сквозная трассировка запроса через границы.
  - **Ф:** как связать в один след событие в JS, запрос к PHP, вызов Python и SQL-запрос?
  - **Г:** один **correlation-id** (`trace_id`), прокинутый в каждом контракте (HTTP-заголовок, поле JSON в пайпе, комментарий-тег в SQL), даёт сборку сквозного следа без тяжёлого трейсинг-стека.
  - **П:** прототип: JS генерит `trace_id`, он логируется на каждой границе; греп по `trace_id` собирает полный путь одного запроса. Метрика — можно ли восстановить путь по логам за < 1 мин.
- **Q4.2** 🟡 Единый формат логов на всех языках.
  - **Ф:** как сделать логи PHP/Python/JS сопоставимыми (мерджабельными)?
  - **Г:** структурный JSON-лог (одна строка = один JSON-объект с `ts`, `lvl`, `trace_id`, `lang`, `msg`) на всех языках сводит разнородные логи в один поток без парсеров под каждый формат.
  - **П:** общий мини-хелпер логирования на каждом языке (как interop-хелпер в [NX-POLY-003#предложение-2](../50-polyglot/NX-POLY-003-interop.md)); проверить мердж и сортировку по `ts` из трёх источников.
- **Q4.3** 🟡 Локализация стыка-виновника.
  - **Ф:** как быстро понять, на какой границе сломался контракт (а не внутри языка)?
  - **Г:** валидация по схеме **на входе каждой границы** (fail-fast, [NX-POLY-003#предложение-3](../50-polyglot/NX-POLY-003-interop.md)) превращает «молчаливую порчу» в явную ошибку *с именем стыка и версией контракта*.
  - **П:** инъекция битого payload на каждой границе; проверить, что ошибка называет стык и `schema_version`, а не падает где-то ниже по стеку.
- **Q4.4** 🟡 Отладка WASM/FFI (нет привычного дебаггера).
  - **Ф:** чем отлаживать Rust→WASM и нативный FFI, где обычные брейкпоинты слабы?
  - **Г:** для WASM — сборка с `debug`-инфо + `console_error_panic_hook` (паника Rust видна в консоли браузера); для FFI — изоляция в отдельный процесс на время отладки (превратить FFI в IPC, Q2.1) и обычный отладчик там.
  - **П:** воспроизвести панику в WASM и убедиться, что стек виден в DevTools; прогнать «спорный» FFI-вызов как отдельный процесс.

```javascript
// games/nexus/shared/engine/trace.js — correlation-id через все границы (набросок Q4.1/Q4.2)

}
export async function call(url, body, trace_id) {
```

### Q5 — Безопасность чужого кода и моддинга
> Песочница для модов и для любого «не нашего» кода в живом мире.
> Корень: [NX-POLY-009](../50-polyglot/NX-POLY-009-scripting-modding-layer.md).
> Связан с этикой/приватностью [NX-RND-001#T5.3](NX-RND-001-research-agenda.md#T5).

- **Q5.1** 🔴 Модель угроз моддинга.
  - **Ф:** что именно мод может сломать — клиент игрока, сервер, других игроков, данные?
  - **Г:** наибольший риск — **серверный** мод-код (доступ к БД/файлам/сети) и **межигроковый** (чит/инъекция в общий мир, см. эхо-мультиплеер [NX-INN-003](../20-innovation/NX-INN-003-echo-multiplayer.md)); клиентский мод вредит в основном самому моддеру.
  - **П:** STRIDE-таблица по каждому слою (клиент/сервер/общий мир/данные); ранжировать по «ущерб × вероятность»; это вход для Q5.2–Q5.4.
- **Q5.2** 🔴 Изоляция исполнения мода.
  - **Ф:** в какой песочнице гонять чужой код — WASM-сэндбокс, встроенный Lua с урезанным окружением, отдельный процесс с лимитами?
  - **Г:** **WASM** даёт лучшую изоляцию по памяти из коробки (нет доступа к хосту без явных импортов); **Lua** удобнее моддерам, но требует ручного «обрезания» (`os`, `io`, `loadstring` запрещены). Для серверных модов — обязательно отдельный процесс с лимитами CPU/RAM/времени.
  - **П:** прототип: мод на Lua с whitelisted-API vs мод на WASM с явными импортами; красная команда пробует выйти из песочницы (файлы, сеть, бесконечный цикл); метрика — число успешных побегов.
- **Q5.3** 🟡 Capability-модель прав мода.
  - **Ф:** как дать моду ровно нужные возможности и ни одной лишней?
  - **Г:** мод получает **только явно переданные функции-импорты** (capability-style), а не глобальный доступ; «прочитать состояние клетки» — да, «открыть файл» — нет такого импорта вовсе.
  - **П:** описать манифест мода (`permissions: [read_world, spawn_particle]`); проверить, что вызов незаявленной возможности невозможен физически (её нет в окружении), а не просто запрещён проверкой.
- **Q5.4** 🟡 Выбор языка модов (DSL vs полноценный). → [NX-POLY-009](../50-polyglot/NX-POLY-009-scripting-modding-layer.md), связан с [NX-RND-001#T4.2](NX-RND-001-research-agenda.md#T4)
  - **Ф:** дать моддерам ограниченный DSL/Lua-таблицы или полноценный язык (Lua/JS-в-WASM)?
  - **Г:** двухуровнево: **декларативный DSL** (данные: предметы, рецепты, правила экологии) покрывает 80 % модов безопасно; **скриптовый уровень** (Lua/WASM в песочнице) — для оставшихся 20 %, и только он требует Q5.2–Q5.3.
  - **П:** разметить корпус гипотетических модов по «декларативно достаточно / нужен скрипт»; проверить долю 80/20; согласовать с контент-DSL ([NX-RND-001#T4.2](NX-RND-001-research-agenda.md#T4)).
- **Q5.5** 🟡 Лимиты ресурсов и анти-DoS.
  - **Ф:** как не дать моду повесить игру бесконечным циклом или памятью?
  - **Г:** жёсткие лимиты — «бюджет инструкций/кадр» (fuel в WASM-рантайме / счётчик в Lua-хуке) + потолок памяти + таймаут; превышение → мод останавливается, мир продолжает жить.
  - **П:** мод с `while true do end` и мод-«пожиратель памяти»; убедиться, что движок их прерывает в пределах кадрового бюджета, а не зависает.
- **Q5.6** 🟡 Доверие, подпись и распространение модов.
  - **Ф:** как отличать доверенный мод от случайного и где граница «sandbox достаточно / нужна ревизия»?
  - **Г:** sandbox (Q5.2) — первичная защита и не требует доверия; подпись/репутация — вторичный слой для серверных модов, влияющих на общий мир; чисто клиентский мод подписи не требует.
  - **П:** политика-матрица «слой воздействия × требуется подпись?»; красная команда проверяет, достаточно ли одной песочницы без подписи для клиентского мода.

```python
# tools/run_mod.py — серверный мод в ОТДЕЛЬНОМ процессе с лимитами (Q5.2/Q5.5, POSIX)
import resource, subprocess, json

def run_mod_sandboxed(mod_path: str, world_state: dict, timeout_s: float = 0.5) -> dict:
    def limit():                                    # лимиты применяются в дочернем процессе
        resource.setrlimit(resource.RLIMIT_CPU, (1, 1))               # 1 c CPU
        resource.setrlimit(resource.RLIMIT_AS, (256 * 1024 * 1024,) * 2)  # 256 МБ RAM
    proc = subprocess.run(
        ["lua", "tools/mod_host.lua", mod_path],    # хост обрезает окружение Lua (whitelist)
        input=json.dumps(world_state), capture_output=True, text=True,
        timeout=timeout_s, preexec_fn=limit,        # таймаут + rlimit = анти-DoS
    )
    return json.loads(proc.stdout)                  # контракт выхода валидируется по схеме (Q4.3)
```

### Вариант B (рекомендуется). Узел = гипотеза + воспроизводимый бенч-скрипт
К каждому числовому узлу (Q1.2, Q1.3, Q2.1–Q2.3, Q5.5) прилагается крошечный
бенч/тест в `tools/bench/`, который печатает измеренное число и сравнивает с порогом
гипотезы. Тогда статус узла (🔴/🟡/🟢) **выводится из факта прогона**, как статусы
повестки в [NX-RND-001#предложения](NX-RND-001-research-agenda.md) (Вариант B там).

```python
# tools/bench/q1_3_php_python_boundary.py — измеряет порог CLI-пайп vs HTTP (Q1.3)
import subprocess, time, statistics

def time_n(fn, n=50):
    xs = []
    for _ in range(n):
        t = time.perf_counter(); fn(); xs.append(time.perf_counter() - t)
    return statistics.median(xs) * 1000  # мс

pipe_ms = time_n(lambda: subprocess.run(["python", "-c", "pass"]))  # старт интерпретатора
print(f"Q1.3: старт CPython ~{pipe_ms:.1f} мс/вызов; "
      f"порог гипотезы — выгода HTTP при >~{1000/pipe_ms:.0f} вызовов/сек")
```

## Риски, открытые вопросы
- **Пороговые числа — гипотезы, не факты.** Все «~15 %», «~1 мс», «4–5 языков» —
  кандидаты на проверку (Вариант B), а не измеренные значения. Маркировать как
  предположения, пока нет прогона.
- **Q4/Q5 — белые пятна повестки.** Отладка и моддинг-безопасность не были выделены в
  плоской T1; их полнота тут не гарантирована — ветки нужно пополнять.
- **Дрейф между этим деревом и [NX-RND-001](NX-RND-001-research-agenda.md).** Таблица
  соответствия (T1.* ↔ Q*) должна обновляться при правке любого из двух деревьев;
  кандидат на авто-сверку скриптом (как сканер в [NX-RND-001#предложения](NX-RND-001-research-agenda.md)).
- **Безопасность моддинга недооценить легко.** Q5 — самая «дорогая ошибка»: пропущенный
  побег из песочницы дороже любого перформанс-промаха. Требует красной команды, не только
  бенча.
- **Спор за владение узлом.** Перекрёстные рёбра (Q2.1↔Q4.4 и др.) релевантны нескольким
  POLY-докам — нужна конвенция «главный владелец + соисполнители» (как в
  [NX-RND-001#risks](NX-RND-001-research-agenda.md)).
