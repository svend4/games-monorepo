# Межъязыковая интероперабельность: механизмы стыковки языков

## TL;DR
Языки в NEXUS не «дружат волшебно» — они общаются через **семь проверенных каналов**:
HTTP/JSON, stdin/stdout-пайпы, файлы-контракты, FFI (C ABI), WASM-импорты, codegen из
единой схемы и очереди/сокеты. Этот документ даёт **таблицу выбора** «механизм → когда
уместен → цена» и рабочие примеры (PHP↔Python через CLI и HTTP; JS↔Rust через WASM).
«Велосипед с крылышками»: транспорты — давно изобретённое колесо, новое измерение —
**дисциплина контрактов** на каждом стыке монорепо.

## Краткое содержание
[NX-POLY-001](NX-POLY-001-language-per-role.md) отвечает на вопрос «*какой* язык под
роль». Этот документ отвечает на следующий вопрос — «*как* эти языки разговаривают, не
теряя данных и не превращая стык в источник багов». В монорепо уже сосуществуют клиент
на HTML/JS (`games/nexus/shared/**`, `v1-2d-mmo/game.html`), бэкенд на PHP
(`nexus_api.php`), схема на SQL (`nexus_setup.sql`), генераторы контента на Python и
источник истины на Markdown (`design/**`). Каждая пара таких слоёв нуждается в канале
связи. Мы утверждаем: **каналов мало (≈7), их свойства известны, и выбор сводится к
таблице**, а не к импровизации.

Главный тезис: interop — это не транспорт, а **контракт**. Транспорт (HTTP, пайп, файл,
ABI) — проверенный кирпичик. Контракт (схема JSON, сигнатура CLI, ABI WASM, DDL таблицы)
— то, что мы дисциплинируем и, где можно, **генерируем из единого источника** (см.
[NX-SPEC-003](../40-specs/NX-SPEC-003-echo-protocol.md)).

## Расширенное содержание (общее)

### Два измерения выбора канала
Любой стык характеризуется двумя осями:

1. **Граница процесса.** Языки в одном процессе (JS+WASM, PHP+расширение на C) или в
   разных (PHP-процесс ↔ Python-процесс)? Внутри процесса — FFI/WASM (нанесекунды,
   но опасно); между процессами — пайпы/HTTP/файлы/очереди (микро-миллисекунды, но
   изолированно и безопасно).
2. **Темп и связность.** Запрос-ответ синхронно (HTTP, CLI), поток данных (пайп),
   обмен большими редко меняющимися артефактами (файл-контракт), или развязанный во
   времени поток событий (очередь)?

Из этих осей вытекает короткий каталог механизмов.

### Каталог из семи механизмов

1. **HTTP/JSON API** — сетевой запрос-ответ между процессами/машинами. Универсальный
   эсперанто: любой язык умеет отправить и принять JSON по HTTP. Это уже основной канал
   клиент↔бэкенд (`fetch` из JS → `nexus_api.php`).
2. **stdin/stdout-пайпы (Unix)** — один процесс запускает другой, шлёт вход в stdin,
   читает результат из stdout. Идеален для «вызвать инструмент на другом языке разово»:
   PHP вызывает Python-скрипт генерации, читает JSON из его stdout.
3. **Файлы-контракты** — обмен через общий артефакт на диске (JSON/CSV/SQL/Markdown).
   Python-генератор пишет `levels.json`, JS-клиент его читает. Развязка во времени,
   воспроизводимость, версионирование в git.
4. **FFI (Foreign Function Interface)** — вызов нативной функции по C ABI из другого
   языка в **том же процессе** (PHP FFI → `.so`/`.dll`, Python `ctypes`/`cffi`).
   Максимум скорости, максимум ответственности (память, краши).
5. **WASM-импорты** — компиляция Rust/AssemblyScript/Zig → WASM-модуль, который JS
   импортирует и зовёт как обычные функции. Безопасная песочница + почти нативная
   скорость в браузере. Горячие пути клиента (см. [NX-POLY-001](NX-POLY-001-language-per-role.md#details)).
6. **Codegen из единой схемы** — не транспорт, а **мета-механизм**: одна схема (JSON
   Schema / `.proto` / SQL DDL) порождает типы/валидаторы/клиентов на всех языках.
   Убивает дрейф контрактов в зародыше. Детали — [NX-SPEC-003](../40-specs/NX-SPEC-003-echo-protocol.md).
7. **Очереди и сокеты** — развязанный во времени (очередь: Redis/файловая очередь) или
   постоянный двунаправленный (WebSocket/TCP) канал. Для real-time MMO-событий и
   фоновых задач (генерация мира воркером на Python, пока игрок играет).

### Принцип «узкой талии» (narrow waist)
Как у Unix «всё есть текст», а у IP «всё есть пакет», у нас должна быть **узкая талия —
JSON-over-что-угодно** как канал по умолчанию. Любой стык, для которого нет жёсткого
требования по скорости, использует JSON: по HTTP, через пайп или в файле. Это даёт
один формат сериализации на 90% связей и сводит зоопарк к управляемому набору. FFI/WASM
— исключения, оправданные только профилем производительности.

## Детали и частные случаи

### Таблица выбора: механизм → когда уместен → цена

| Механизм | Когда уместен | Латентность | Цена / риски | Пример в NEXUS |
|---|---|---|---|---|
| **HTTP/JSON** | Клиент↔сервер, сервис↔сервис, разные машины; нужна сеть и язык-агностичность | ~1–50 мс | Сериализация, сетевые ошибки, нужно версионировать API | JS `fetch` → `nexus_api.php` |
| **stdin/stdout-пайп** | Разовый вызов инструмента на др. языке локально; батч-обработка потока | ~5–50 мс (старт процесса) | Старт процесса дорог; экранирование аргументов; только локально | PHP `proc_open` → Python-генератор |
| **Файл-контракт** | Большие редкие артефакты; нужна воспроизводимость и git-история; развязка во времени | секунды (батч) | Устаревание данных; кто-то должен «пересобрать»; гонки записи | Python пишет `data/level1.js`/`*.json`, JS читает |
| **FFI (C ABI)** | Горячая нативная либа в одном процессе; уже есть `.so`/`.dll` | ~наносекунды | Краши/утечки рушат хост-процесс; ручное управление памятью; платформозависимость | PHP FFI → нативная физика/крипто (опционально) |
| **WASM-импорт** | Горячий путь в браузере; нужна песочница + скорость; портируемость | ~наносекунды | Сборочный конвейер (toolchain); маршалинг через линейную память; размер модуля | JS ↔ Rust (pathfinding, шум, симуляция) |
| **Codegen из схемы** | Любой стык, где контракт важнее транспорта; ≥2 языка делят структуру | (сборка) | Нужен build-step и единый источник схемы; кривая входа | JSON Schema → TS-типы + PHP-валидатор + SQL DDL |
| **Очередь / сокет** | Real-time события (MMO); фоновые долгие задачи; развязка producer/consumer | ~1–10 мс (сокет) / отложенно (очередь) | Инфраструктура (брокер); семантика доставки (at-least-once); порядок | WebSocket мир-события; файловая очередь задач воркеру |

**Правило выбора одной строкой:** *в одном процессе и нужна скорость → WASM (браузер)
или FFI (сервер); между процессами и нужен ответ сейчас → HTTP или CLI-пайп; обмен
большими артефактами без спешки → файл-контракт; поток событий во времени → очередь/сокет.
Контракт на стыке — всегда из codegen, если структуру делят ≥2 языка.*

### Частный случай: PHP ↔ Python

В NEXUS PHP — это «горячий» онлайн-слой (`nexus_api.php`), а Python — оффлайн-генерация
контента и симуляции баланса. Между ними два режима связи.

**(A) Разовый локальный вызов — CLI-пайп.** PHP-эндпоинт хочет получить сгенерированный
контент от Python один раз. Используем stdin (JSON-вход) → stdout (JSON-выход):

```python
# tools/gen_loot.py — Python как чистая функция: stdin JSON -> stdout JSON
import sys, json

def generate(seed: int, tier: int) -> dict:
    # детерминированная генерация по seed (без побочных эффектов)
    rng = __import__("random").Random(seed)
    items = [{"id": f"item_{i}", "rarity": rng.choice(["common", "rare", "epic"])}
             for i in range(tier * 3)]
    return {"seed": seed, "tier": tier, "items": items}

def main() -> None:
    req = json.load(sys.stdin)            # контракт входа: {"seed": int, "tier": int}
    out = generate(req["seed"], req["tier"])
    json.dump(out, sys.stdout)            # контракт выхода: {"seed","tier","items":[...]}

if __name__ == "__main__":
    main()
```

```php
<?php
// nexus_api.php (фрагмент): вызов Python-генератора через пайп
function call_python(string $script, array $payload): array {
    $descriptors = [
        0 => ['pipe', 'r'],   // stdin  для дочернего процесса
        1 => ['pipe', 'w'],   // stdout от дочернего процесса
        2 => ['pipe', 'w'],   // stderr (логируем отдельно)
    ];
    $proc = proc_open(['python', $script], $descriptors, $pipes);
    if (!is_resource($proc)) {
        throw new RuntimeException("cannot start python");
    }
    fwrite($pipes[0], json_encode($payload));   // шлём JSON в stdin
    fclose($pipes[0]);
    $stdout = stream_get_contents($pipes[1]);    // читаем JSON из stdout
    $stderr = stream_get_contents($pipes[2]);
    fclose($pipes[1]); fclose($pipes[2]);
    $code = proc_close($proc);
    if ($code !== 0) {
        error_log("python failed: $stderr");
        throw new RuntimeException("python exit $code");
    }
    return json_decode($stdout, true);           // контракт выхода
}

$loot = call_python('tools/gen_loot.py', ['seed' => 12345, 'tier' => 3]);
```

> Цена пайпа: каждый вызов поднимает процесс Python (десятки мс на старт интерпретатора).
> Уместно для редких/батч-вызовов. Для частых — режим (B).

**(B) Частый онлайн-вызов — HTTP-микросервис.** Если PHP дёргает Python в горячем пути,
держим Python как долгоживущий HTTP-сервис (Flask/FastAPI) и общаемся JSON-ом по HTTP —
старт процесса платится один раз:

```python
# tools/gen_service.py — Python-генератор как HTTP-сервис
from flask import Flask, request, jsonify
from gen_loot import generate            # переиспользуем ту же чистую функцию
app = Flask(__name__)

@app.post("/loot")
def loot():
    req = request.get_json()              # тот же контракт входа
    return jsonify(generate(req["seed"], req["tier"]))

# запуск: flask --app gen_service run --port 8077
```

```php
<?php
// PHP зовёт Python-сервис по HTTP — без старта процесса на каждый запрос
function http_json(string $url, array $body): array {
    $ch = curl_init($url);
    curl_setopt_array($ch, [
        CURLOPT_POST => true,
        CURLOPT_HTTPHEADER => ['Content-Type: application/json'],
        CURLOPT_POSTFIELDS => json_encode($body),
        CURLOPT_RETURNTRANSFER => true,
        CURLOPT_TIMEOUT => 2,
    ]);
    $resp = curl_exec($ch);
    if ($resp === false) { throw new RuntimeException(curl_error($ch)); }
    curl_close($ch);
    return json_decode($resp, true);
}

$loot = http_json('http://127.0.0.1:8077/loot', ['seed' => 12345, 'tier' => 3]);
```

**Ключевое наблюдение:** контракт входа/выхода (`{seed,tier} → {seed,tier,items}`)
**один и тот же** для пайпа и HTTP. Транспорт меняется, контракт — нет. Это и есть
дисциплина: контракт описан один раз (в идеале — JSON Schema, см.
[NX-SPEC-003](../40-specs/NX-SPEC-003-echo-protocol.md)), транспорт выбирается по
профилю нагрузки.

### Частный случай: JS ↔ Rust через WASM

Горячие пути клиента (поиск пути по сетке, процедурный шум, проверка коллизий пачкой)
выразительнее и быстрее на Rust, скомпилированном в WASM, чем на JS. Контракт — это
**экспортируемые функции и линейная память** модуля.

```rust
// crates/grid/src/lib.rs — Rust-ядро для поиска пути; компилируется в WASM
#[no_mangle]
pub extern "C" fn heuristic(ax: i32, ay: i32, bx: i32, by: i32) -> i32 {
    // манхэттенская эвристика A* — простая чистая функция через границу ABI
    (ax - bx).abs() + (ay - by).abs()
}

// Для массивов работаем через линейную память: возвращаем длину,
// данные кладём в заранее выделенный буфер (см. экспорт alloc ниже).
#[no_mangle]
pub extern "C" fn alloc(len: usize) -> *mut u8 {
    let mut buf = Vec::<u8>::with_capacity(len);
    let ptr = buf.as_mut_ptr();
    std::mem::forget(buf);                 // отдаём владение JS-стороне
    ptr
}
```

Сборка: `cargo build --target wasm32-unknown-unknown --release` (или `wasm-pack` для
готовых JS-биндингов). Загрузка и вызов из клиента:

```javascript
// games/nexus/shared/engine/wasmGrid.js — JS импортирует WASM как обычный модуль
export async function loadGrid(url) {
  const { instance } = await WebAssembly.instantiateStreaming(
    fetch(url),
    { env: { /* импорты, если Rust зовёт обратно в JS */ } }
  );
  const { heuristic, alloc, memory } = instance.exports;

  return {
    // скалярный вызов: числа проходят через ABI напрямую, маршалинг не нужен
    heuristic: (ax, ay, bx, by) => heuristic(ax, ay, bx, by),

    // массив: пишем в линейную память WASM, передаём указатель+длину
    writeCells(cells /* Int32Array */) {
      const ptr = alloc(cells.length * 4);
      new Int32Array(memory.buffer, ptr, cells.length).set(cells);
      return ptr;                          // дальше передаём ptr в другие экспорты
    },
  };
}
```

> Цена WASM: (1) сборочный конвейер Rust→WASM в [NX-SYS-003](../30-systems/NX-SYS-003-content-pipeline.md);
> (2) **маршалинг** — числа проходят бесплатно, а строки/массивы/структуры нужно
> копировать через линейную память (`memory.buffer`). Поэтому через границу гоняем
> «толстые» вызовы (обработать весь массив клеток за один заход), а не миллион мелких.

### Граничные случаи и подводные камни

- **Экранирование в CLI-пайпах.** Никогда не склеивай аргументы строкой shell — передавай
  данные через **stdin как JSON**, а аргументы — массивом (`proc_open(['python', $script])`,
  не `"python $script $arg"`). Иначе инъекция и поломка на пробелах/кавычках.
- **Кодировки.** JSON — всегда UTF-8 без BOM. Особенно важно на стыке с PHP/Windows, где
  файлы легко получают BOM (см. заметку про `Out-File -Encoding utf8` в окружении).
- **Числа.** JS-`number` — это f64; целые `> 2^53` теряют точность. Большие id/деньги
  передавай строками. SQL `BIGINT` ↔ JSON — частая дыра.
- **Память в FFI/WASM.** Кто выделил — тот освобождает; договорись об этом в контракте
  (`alloc`/`free` на стороне модуля). Утечка в долгоживущем процессе = смерть по OOM.
- **Версионирование контракта.** У HTTP-API и файлов-контрактов должно быть поле
  `schema_version`; потребитель проверяет его и деградирует понятно, а не падает.
- **Гонки записи файла-контракта.** Пиши во временный файл и `rename` (атомарно на одном
  томе), чтобы читатель никогда не увидел полузаписанный JSON.

## Предложения и варианты реализации

### Предложение 1: «JSON — узкая талия по умолчанию»
Все стыки, кроме явно горячих, используют JSON. Один сериализатор, один валидатор-контракт,
один способ логировать «что прошло по стыку». Горячие пути (WASM/FFI) — задокументированный
список исключений, а не норма.

### Предложение 2: единый хелпер на каждом языке
Свести варианты транспорта к 2–3 функциям-врапперам, чтобы код стыка был одинаков:

```pseudo
// общий интерфейс interop на каждом языке
interop.http(url, json)      -> json     // HTTP/JSON
interop.cli(script, json)    -> json     // stdin/stdout-пайп
interop.readArtifact(path)   -> json     // файл-контракт (чтение)
interop.writeArtifact(path, json)        // файл-контракт (атомарная запись через temp+rename)
```

Тогда смена транспорта = смена одной строки вызова, контракт не трогается.

### Предложение 3: контракт-реестр и валидация на границе
Каждый стык регистрирует свой контракт (JSON Schema) в `design/40-specs` и валидирует
данные **на входе** (fail fast). Где языков ≥2 — генерируем код контракта (codegen,
[NX-SPEC-003](../40-specs/NX-SPEC-003-echo-protocol.md)), а не пишем валидаторы руками.

```pseudo
// на любом стыке — валидация по схеме до использования
fn handle(raw):
    data = json.parse(raw)
    assert validate(data, schema["loot_request@v1"])   // codegen'нутый валидатор
    return process(data)
```

### Предложение 4: матрица транспортов под нагрузку
Для каждой пары слоёв заранее решено, какой транспорт при каком темпе:

```pseudo
choose_transport(call):
    if same_process and call.hot:        return FFI if server else WASM
    if cross_process and call.sync:      return CLI_PIPE if rare else HTTP
    if bulk_artifact and not call.sync:  return FILE_CONTRACT
    if stream_of_events:                 return SOCKET if realtime else QUEUE
```

### Альтернативы, рассмотренные и отклонённые (пока)
- **gRPC/Protobuf везде.** Строгие контракты и скорость, но тяжёлый toolchain и хуже
  «играется» с PHP/браузером, чем JSON. Держим как кандидата для будущего сервис-слоя.
- **Общая БД как шина.** Заманчиво (SQL уже есть), но БД как очередь — антипаттерн на
  масштабе; оставляем БД для данных, события — через очередь/сокет.
- **Эмбеддинг интерпретатора** (Python внутри PHP-процесса). Хрупко и связно; пайп/HTTP
  дают ту же возможность с изоляцией.

## Что нового и какие кирпичики
- **НОВОЕ:** не транспорт, а **карта выбора** «механизм → когда уместен → цена» и
  дисциплина «контракт отдельно от транспорта» для конкретного монорепо NEXUS. Новое
  измерение поверх старого: транспорты известны десятилетиями — мы добавляем
  *систематический выбор* и *генерируемые контракты*, чтобы стыки не текли.
- **Источники:** `c20-proven` (Unix-пайпы и философия «текст как универсальный
  интерфейс», C ABI/FFI, HTTP), `humanities` (идея «узкой талии»/lingua franca и
  «контракта» как социального института — переносим на технический стык).
- **Проверенные кирпичики:** HTTP/JSON; stdin/stdout-пайпы (`proc_open`, `subprocess`);
  файлы-контракты (JSON/CSV/SQL/Markdown в git); FFI по C ABI (PHP FFI, Python `ctypes`);
  WASM-импорты (`WebAssembly.instantiateStreaming`, линейная память); codegen из схемы
  (JSON Schema/proto/DDL); очереди/сокеты (WebSocket, файловая/Redis-очередь).
- **Чего нет в других играх (или редко):** игровые проекты обычно либо монолитны на
  одном движке, либо клеят языки ad-hoc. Здесь — *явный реестр стыков с ценой и
  контрактом*, где «как соединить X и Y» становится табличным решением, а не творчеством
  каждого разработчика заново.

## Риски, открытые вопросы
- **Старт процесса в CLI-пайпах** дорог; нужна метрика «частота вызова», чтобы вовремя
  мигрировать на HTTP-сервис (B). Открыто: где порог?
- **Маршалинг WASM** для сложных структур легко съедает выигрыш в скорости; нужен бенч
  «толстый vs тонкий вызов» для наших горячих путей.
- **FFI на сервере** рушит весь PHP-процесс при краше нативной либы — стоит ли вообще
  пускать FFI в онлайн-слой или ограничить его оффлайн-тулингом?
- **Дрейф контрактов** без codegen неизбежен; codegen ([NX-SPEC-003]) — `analyzed`, не
  `prototyped`. Открыто: какой единый формат схемы (JSON Schema vs proto) выбрать.
- **Очереди/сокеты** тянут инфраструктуру (брокер, переподключения, семантику доставки) —
  не раздуть ли это деплой ([NX-SYS-003])?
- **Версионирование** контрактов: договориться о едином поле (`schema_version`) и политике
  обратной совместимости — пока не зафиксировано.

## Комментарии
Комментирует выбор стека в `NX-ARCH#sec-stack` и ревью `NX-REVIEW#stack`: подтверждает
полиглот-факт, но настаивает, что узкое место — *стыки*, а не языки. Дополняет
[NX-POLY-001](NX-POLY-001-language-per-role.md) («какой язык») ответом «как соединить».
Развёрнутые ветки — при необходимости вынести в `NX-CMT-###`.
