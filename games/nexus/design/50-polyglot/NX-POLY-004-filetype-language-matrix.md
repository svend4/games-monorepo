# Матрица «тип файла → язык/инструмент»

## TL;DR
Каждый **тип файла** (расширение) однозначно отображается в **язык/инструмент**, его
**роль** в системе, **проверенную альтернативу** (как делают все) и **инновационное
измерение** (одно «крылышко» поверх проверенного). Это табличный «велосипед с крылышками»:
колесо — устоявшаяся конвенция «расширение → тулчейн» (десятилетия Unix/веб-стека), новое
измерение — нормативная карта, которая ещё и фиксирует *interop-контракт* для каждого
типа, чтобы стыки между языками не текли. Дополняет карту ролей из
[NX-POLY-001](NX-POLY-001-language-per-role.md), но смотрит снизу — от артефакта на диске.

## Краткое содержание
[NX-POLY-001](NX-POLY-001-language-per-role.md) отвечает на вопрос «какой *слой* на каком
языке». Этот документ отвечает на симметричный, более приземлённый вопрос: **«я вижу файл
с таким расширением — чем его открывать, кто его пишет, кто читает, и через какой контракт
он соединяется с другими?»**. Для каждого типа даётся: основной инструмент, роль в трёх
зонах исполнения (runtime браузера / серверная граница / оффлайн-конвейер — см.
[NX-POLY-001#три-зоны-исполнения](NX-POLY-001-language-per-role.md)), проверенная
альтернатива, инновационная альтернатива и пример кода/команды.

Монорепо NEXUS уже содержит почти все эти типы: `.md` в `design/**` (источник истины),
`.html`/`.js` в `v1-2d-mmo/game.html` и `shared/**`, `.php` (`nexus_api.php`), `.sql`
(`nexus_setup.sql`), `.json`/`.csv` как обменные данные, Python-генераторы. Матрица
канонизирует то, что уже стихийно сложилось, и заранее размечает места под будущие
«крылышки» (`.rs`/`.wasm`, `.lua`, `.glsl`, `.pl`).

## Расширенное содержание (общее)

### Зачем матрица, если есть карта ролей
Карта ролей (NX-POLY-001) — это взгляд архитектора сверху. Матрица типов файлов — взгляд
контрибьютора/инструмента снизу. Они двойственны, но не избыточны: роль может реализоваться
несколькими типами файлов (роль «контент» = `.md` + `.json` + `.csv`), а один тип файла
может играть разные роли в зависимости от зоны (`.js` — и runtime-клиент, и build-time
codegen-артефакт). Lookup по расширению — то, что реально делает редактор, линтер, сборщик
и новый человек в репозитории. Поэтому матрица — **первичный операционный артефакт**, а
карта ролей — концептуальный.

### Главная матрица: тип файла → язык/инструмент → роль → проверенное → инновация

| Тип / расш. | Язык/инструмент | Роль в системе | Зона | Проверенная альтернатива (как у всех) | Инновационное измерение (крылышко) | Interop-контракт |
|---|---|---|---|---|---|---|
| `.md` | Markdown (+ front-matter YAML) | Источник истины: дизайн-вики, дока, контент-нарратив | offline | README/Wiki-страницы вручную | **MD как исполнимый источник**: front-matter → codegen в `.json`/`.sql`; lint-граф ссылок (как в этой вики) | файл = контракт; парсится Python/Perl |
| `.json` | JSON | Конфиг и данные времени выполнения, обменный формат | все три | конфиг в коде/`.env` | **JSON Schema как единый контракт** между JS/PHP/Python + версионирование артефактов | `fetch`→JSON, `json_encode`, `json.dumps` |
| `.yaml`/`.yml` | YAML | Человекописанные конфиги/данные, front-matter | offline | JSON-конфиги | YAML — вход, **компилируется** в `.json` для runtime (люди пишут YAML, машина ест JSON) | codegen YAML→JSON в `tools/` |
| `.toml` | TOML | Манифесты/настройки тулчейна (Rust `Cargo.toml`, конфиги) | offline | `.ini`/`.json` | единый «манифест проекта-в-проекте» (см. [NX-POLY-002](NX-POLY-002-project-in-project.md)) | читается сборщиком |
| `.py` | Python | Генерация контента, симуляции баланса, ML, ETL | offline | ручной ввод данных / скрипты на JS | **оффлайн-оракул баланса**: numpy/scipy считает таблицы, пишет артефакты | пишет `.json`/`.js`/`.sql`; stdin/stdout |
| `.php` | PHP | Бэкенд/API/SSR, серверная граница | server | Node-бэкенд | PHP остаётся тонкой границей; тяжёлое — в очередь к воркеру (не `exec()` на запрос) | HTTP/JSON, PDO→SQL |
| `.pl`/`.pm` | Perl | Тяжёлый текст, regex, склейка пайплайнов (ETL-клей) | offline | `sed`/`awk`/скрипты на Python | Perl как «клей» между шагами codegen — one-liner вместо 30 строк | stdin/stdout пайпы |
| `.js` | JavaScript | Клиент: рендер, UI, игровая логика | browser | то же (универсально) | **общий контракт клиент/сервер** через схему данных, чтобы не дублировать логику | DOM-события, `fetch`, ES-модули |
| `.ts`/`.d.ts` | TypeScript | Типобезопасность клиента (постепенно) | browser/offline | «голый» JS | TS вводится **через JSDoc + `// @ts-check`**, без обязательной компиляции на старте | `.d.ts` как контракт типов |
| `.mjs` | JS ES-модуль | Изоморфные утилиты / build-скрипты на Node | offline/browser | CommonJS | один и тот же модуль в браузере и в build-time (изоморфизм) | импорт/экспорт ES |
| `.rs` | Rust → `.wasm` | Горячие пути: worldgen, pathfinding, физика | browser(WASM) | та же логика на JS (медленнее) | **детерминированный near-native** в браузере без переписывания движка | WASM ABI, shared memory |
| `.wasm` | WebAssembly (бинарь) | Артефакт горячего пути, грузится в JS | browser | нет (или asm.js) | разделяемый бинарь как «общий мозг» для одинаковой логики | `WebAssembly.instantiate` |
| `.ts` (AssemblyScript) | AssemblyScript → `.wasm` | «Почти TS» путь к WASM без Rust-тулчейна | browser(WASM) | Rust | низкий порог входа к WASM для TS-команды | `asc` → `.wasm` |
| `.lua` | Lua | Моддинг, пользовательские скрипты в песочнице | browser(sandbox) | hardcoded-механики / `eval` | **песочница с host-API** — моддинг без RCE; Lua встраивают в игры с 1990-х | host-функции, sandbox-API |
| `.sql` | SQL (MySQL/SQLite) | Схема и данные БД, миграции | server | ORM-модели в коде | схема как **декларативный контракт**, общий источник для клиент/серверной валидации | DDL, prepared statements |
| `.glsl`/`.vert`/`.frag` | GLSL | Шейдеры: частицы, пост-обработка, эффекты | browser(GPU) | Canvas2D-эффекты на CPU | GPU-эффекты как «крылышко» к существующему рендеру | uniforms/attributes, WebGL |
| `.csv` | CSV | Табличный обмен: баланс, локализация, экспорт аналитики | offline | ручные таблицы в коде | CSV как **редактируемый дизайнером контракт** (Excel/Sheets ↔ git) → codegen | парсится Python/Perl/PHP |
| `.wgsl` | WGSL (WebGPU) | Шейдеры нового поколения (опц., будущее) | browser(GPU) | GLSL/WebGL | задел под WebGPU, когда созреет | WebGPU-пайплайн |
| `.png`/`.webp`/atlas | PNG/WebP + JSON-атлас | Спрайты/текстуры + метаданные раскладки | browser | отдельные картинки | **генерируемый атлас** (Python/PIL пишет PNG+JSON одним проходом) | `<img>`/WebGL + JSON-атлас |
| `.wat` | WebAssembly Text | Отладка/ручная микрооптимизация WASM | offline | дизассемблер | человекочитаемый WASM для аудита горячего пути | `wat2wasm` |

> Принцип чтения матрицы: **колонка «Проверенная альтернатива» — это колесо** (как делают
> все, надёжно), **колонка «Инновационное измерение» — крылышко** (одно новое свойство
> поверх колеса, добавляется только по доказанной нужде). Никогда не добавляем крылышко,
> пока колесо не крутится. См. философию в [NX-INN-001](../20-innovation/NX-INN-001.md).

### Три «семьи» типов файлов
Чтобы матрица не выглядела плоским списком, типы группируются по природе:

1. **Данные-как-контракт** (`.json`, `.yaml`, `.toml`, `.csv`, `.sql`, `.md`-front-matter):
   декларативны, diff-friendly, читаются несколькими языками. Главное правило —
   *данные не пишутся императивным кодом*.
2. **Код зоны runtime** (`.js`, `.ts`, `.wasm`/`.rs`/AssemblyScript, `.glsl`, `.lua`):
   грузится в браузер. Жёсткое требование зоны (см. NX-POLY-001).
3. **Код оффлайн-конвейера** (`.py`, `.pl`, build-`.mjs`, `.wat`): производит **артефакты**,
   не работает в проде во время игры.

Предохранитель тот же, что в NX-POLY-001: файл из семьи (3) **никогда** не оказывается в
горячем цикле; он лишь готовит файлы семьи (1), которые потребляет семья (2).

## Детали и частные случаи

### Один тип — несколько ролей (полисемия расширения)
`.js` — самый перегруженный тип. Он бывает:
- **runtime-клиент** (`shared/systems/CombatSystem.js`) — пишется и читается человеком;
- **сгенерированный артефакт** (`v3-3d/data/level1.js` — продукт Python-генератора, см.
  пример в [NX-POLY-001#минимальные-примеры](NX-POLY-001-language-per-role.md)) —
  **не редактируется руками**, помечается баннером;
- **build-скрипт** (`.mjs` на Node) — оффлайн-конвейер.

Правило различения — **баннер-маркер** в первой строке артефакта:
```js
// AUTOGENERATED by tools/gen_levels.py — DO NOT EDIT. seed=42 gen=1.3.0 2026-06-29
export const LEVEL1 = { /* ... */ };
```
Линтер запрещает ручные правки файлов с таким баннером (открытый вопрос — как именно ловить
в CI, см. ниже).

### `.md` как исполнимый источник истины
Front-matter этой самой вики — пример того, как `.md` перестаёт быть «просто текстом» и
становится **входом для codegen**. Python вытягивает YAML-шапки и строит индекс/граф ссылок:
```python
# tools/build_index.py — читает design/**/*.md, собирает INDEX.json (граф ссылок)
import sys, json, pathlib, yaml
docs = []
for p in pathlib.Path("design").rglob("*.md"):
    text = p.read_text(encoding="utf-8")
    if text.startswith("---"):
        fm = text.split("---", 2)[1]
        meta = yaml.safe_load(fm)
        docs.append({"id": meta["id"], "path": str(p),
                     "relates_to": meta.get("relates_to", [])})
pathlib.Path("design/00-meta/INDEX.json").write_text(
    json.dumps(docs, ensure_ascii=False, indent=2), encoding="utf-8")
```
Это «крылышко» поверх проверенного колеса (Markdown-вики): тот же diff-friendly текст, но с
машинно-проверяемым графом ссылок (`relates_to`/`comments_on` из Конституции §6).

### YAML→JSON: люди пишут одно, машина ест другое
Дизайнер правит читаемый YAML; runtime получает компактный JSON. Контракт — codegen-шаг:
```bash
# tools/yaml2json.pl — Perl-«клей» одной строкой на каждый конфиг
perl -MYAML::XS -MJSON::XS -e 'print encode_json(YAML::XS::LoadFile($ARGV[0]))' \
     config/balance.yaml > data/balance.json
```
Или на Python, если Perl-модули недоступны:
```python
import sys, json, yaml
json.dump(yaml.safe_load(open(sys.argv[1])), open(sys.argv[2], "w"), ensure_ascii=False)
# python tools/yaml2json.py config/balance.yaml data/balance.json
```

### `.csv` как контракт дизайнера баланса
CSV — единственный формат, который одинаково удобно правит и человек в Excel/Sheets, и git,
и три языка сразу. Поэтому таблицы баланса/локализации живут в `.csv`, а в runtime попадают
после codegen:
```csv
id,rarity,weight,base_dmg
sword_iron,common,100,5
sword_flame,rare,20,12
blade_void,legendary,2,40
```
```php
// PHP читает тот же CSV для серверной валидации лута — один источник правды
$rows = array_map('str_getcsv', file('data/loot.csv'));
$header = array_shift($rows);
foreach ($rows as $r) { $loot[] = array_combine($header, $r); }
```
```python
# Python генерирует loot.js для клиента из того же CSV
import csv, json
with open("data/loot.csv", encoding="utf-8") as f:
    rows = list(csv.DictReader(f))
open("data/loot.js","w",encoding="utf-8").write(
    "export const LOOT = " + json.dumps(rows, ensure_ascii=False) + ";")
```
Так клиент (JS), сервер (PHP) и генератор (Python) читают **один** `loot.csv` — нет дубля
логики лута (анти-паттерн из [NX-POLY-001#граничные-случаи-и-анти-паттерны](NX-POLY-001-language-per-role.md)).

### `.sql` как разделяемая декларация
Схема в `nexus_setup.sql` — контракт не только для БД, но и для генераторов: Python может
парсить DDL и порождать TypeScript-типы/JSON-валидаторы (codegen «схема → типы»), чтобы
клиент и сервер не расходились в форме данных.

### `.glsl` и `.lua` — будущие крылышки, размеченные заранее
Их в проекте пока нет, но матрица резервирует им строки и контракты, чтобы при добавлении не
переоткрывать вопрос «куда это положить и как соединить». GLSL — через uniforms/attributes
WebGL; Lua — только через host-API в песочнице (безопасность — отдельная спека угроз,
см. риски NX-POLY-001).

### Таблица выбора: «у меня есть данные X — какой тип файла?»

| Природа данных | Кто правит | Тип файла | Почему |
|---|---|---|---|
| Текстовый дизайн/нарратив/дока | человек | `.md` | diff-friendly, источник истины |
| Конфиг, который правит человек | человек | `.yaml`/`.toml` | читаемость, комментарии |
| Конфиг/данные для runtime | машина | `.json` | парсится всеми, компактно |
| Табличный баланс/локализация | дизайнер | `.csv` | Excel/Sheets ↔ git ↔ 3 языка |
| Реляционные данные с транзакциями | машина | `.sql` | индексы, целостность |
| Сгенерированный код для клиента | машина | `.js` (баннер) | грузится напрямую браузером |
| Горячая логика (профайлер красный) | человек | `.rs`/AssemblyScript→`.wasm` | near-native, детерминизм |
| Пользовательский мод | игрок | `.lua` | песочница, без RCE |
| GPU-эффект | человек | `.glsl` | единственный язык WebGL |

## Предложения и варианты реализации

### Вариант A. «Документ-норматив» (рекомендуемый старт)
Матрица существует как **этот файл** + короткая памятка в корневом README. Никакого тулинга.
Контрибьютор сверяется с таблицей глазами. Risk: low, effort: S. Покрывает 90% пользы —
устраняет споры «чем редактировать/как стыковать».

### Вариант B. «Машинно-проверяемая матрица» (целевой, крылышко)
Матрица выносится в `tools/filetype_matrix.json` и используется линтером/CI:
```json
{
  ".md":   { "tool": "markdown", "zone": "offline", "owner": "human" },
  ".json": { "tool": "json",     "zone": "any",     "owner": "machine|human" },
  ".js":   { "tool": "node",     "zone": "browser", "owner": "human|machine",
             "machine_banner": "AUTOGENERATED" },
  ".rs":   { "tool": "cargo",    "zone": "browser-wasm", "owner": "human" },
  ".csv":  { "tool": "csv",      "zone": "offline", "owner": "designer" }
}
```
Линтер проверяет: артефакты с баннером не редактировались руками; типы из «offline» не
импортируются в runtime-бандл; каждый новый тип файла имеет строку в матрице.
```pseudo
// CI guard: запрет на ручную правку сгенерированного и на runtime-импорт offline-кода
for file in changed_files():
    rule = matrix[ext(file)]
    if rule.machine_banner and head(file).contains(rule.machine_banner) and git_authored_by_human(file):
        fail("Ручная правка сгенерированного артефакта: " + file)
    if rule.zone == "offline" and imported_by_runtime_bundle(file):
        fail("Offline-код просочился в runtime: " + file)
```
Risk: low, effort: M. Добавляется только когда матрица стабилизируется.

### Вариант C. «Генерация скаффолда по типу» (не сейчас)
`new <type> <name>` создаёт файл с правильным баннером, заголовком, и регистрирует контракт.
Преждевременно; зафиксировано как ориентир. Risk: med, effort: L.

### Псевдокод: lookup инструмента по файлу
```pseudo
function toolFor(path):
    e = ext(path)                       // ".js", ".py", ...
    rule = MATRIX[e]
    if rule == null: return "unknown — добавь строку в NX-POLY-004"
    if rule.owner.includes("machine") and head(path).has(rule.machine_banner):
        return rule.tool + " (READ-ONLY: артефакт, правь генератор)"
    return rule.tool
```

## Что нового и какие кирпичики
- **НОВОЕ:** нормативная **матрица типов файлов** с пятью колонками (инструмент / роль / зона
  / проверенная альтернатива / инновационное измерение) и парными колонками «колесо vs
  крылышко» для **каждого** расширения. Новое измерение — не сами расширения (они стары как
  Unix), а то, что выбор инструмента и interop-контракт становятся **табличным lookup'ом** и
  машинно-проверяемым правилом, а не устной договорённостью.
- **Источники:** `c20-proven` (Unix-конвенция «расширение → тулчейн», «файл = контракт»,
  пайпы; SQL как декларативная модель; Lua-встраивание в игры с 1990-х), `humanities` (идея
  *регистра* и *жанра текста* из лингвистики/текстологии — каждый тип файла имеет свой жанр и
  своего «читателя», как письменные регистры языка).
- **Проверенные кирпичики:** Markdown-вики, JSON/JSON Schema, YAML/TOML-конфиги, CSV-обмен,
  SQL DDL + prepared statements, WASM/WebGL/GLSL-пайплайны, codegen, баннеры «do not edit».
  Ничего не изобретается — всё **компонуется** в одну карту.
- **Чего нет в других играх (или редко):** обычно соответствие «расширение → как с ним
  работать» живёт в головах и в `.gitattributes`/линтер-конфигах фрагментарно. Единая
  версионируемая матрица, которая ещё и кодирует interop-контракт и зону исполнения для
  каждого типа (с предохранителем «offline-тип ≠ runtime»), — редкость как первичный
  архитектурный артефакт.

## Риски, открытые вопросы
- **Дрейф матрицы и реальности.** Кто-то добавит `.proto`/`.gd`/`.wgsl` и забудет строку.
  Митигируем guard'ом из варианта B («новый тип без строки = fail CI»). Открыто: где
  канонический источник — этот `.md` или `filetype_matrix.json` (риск двух источников правды).
- **Полисемия `.js`/`.ts`.** Один тип в трёх ролях; различение через баннер хрупко. Открыт
  вопрос — не вынести ли артефакты в отдельный каталог `gen/` вместо баннеров.
- **Ловля ручных правок артефактов в CI.** Нужен надёжный способ отличить машинный коммит от
  человеческого (метка автора? хеш входа в баннере?). Не зафиксировано.
- **YAML/TOML/CSV → JSON codegen.** Добавляет build-шаг и точку отказа; на малом объёме может
  быть оверкилл (тогда — JSON напрямую). Граница «когда оно того стоит» не определена.
- **Канонизация контракта.** Какой формат схемы единый — JSON Schema, `.d.ts` или DDL? Тот же
  открытый вопрос, что в [NX-POLY-001#риски-открытые-вопросы](NX-POLY-001-language-per-role.md);
  матрица его наследует, не решает.
- **Бинарные типы (`.png`/`.wasm`).** git-diff бесполезен; нужна конвенция версионирования
  через сопутствующий `.json`-манифест (seed/версия генератора) — пока не зафиксирована.
