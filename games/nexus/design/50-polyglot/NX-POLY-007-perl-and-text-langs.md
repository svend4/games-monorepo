# Perl и текстовые языки: где они сильны

## TL;DR
Perl и Unix-кирпичики (`awk`, `sed`, `grep`, `jq`) — это не «язык для игры», а **клеевой текстовый слой**: миграции данных, парсинг логов, генерация кода/контента и одноразовые правки целыми деревьями файлов. Берём проверенный десятилетиями инструмент и пристёгиваем к нему «крылышки» — современный пайплайн (git, CI, тесты, `ripgrep`), честно выбирая, где Perl уместен, а где лучше Python.

## Краткое содержание
Монорепо NEXUS уже полиглотно: HTML/JS (клиент), PHP (`nexus_api.php`), Python (генераторы контента), SQL, Markdown (источник истины). Текстовых рутинных задач много: переписать структуру `database.json`, сконвертировать CSV прайсов, переименовать ключи в десятках уровней `level*.js`, выдрать ошибки из логов PHP, сгенерировать boilerplate-документы по шаблону. Для таких задач существует целый класс «текстовых языков» — Perl, AWK, sed, плюс структурный `jq`. Их сила — **в плотности выражения над текстом и потоковой обработке**. Документ даёт реальные примеры команд/кода, таблицу выбора инструмента и честно очерчивает, когда современные альтернативы (Python, `ripgrep`) предпочтительнее. Связан с [NX-POLY-003](NX-POLY-003-stdin-stdout-pipes.md) (пайпы stdin/stdout как механизм interop) и [NX-POLY-004](NX-POLY-004-shared-data-files.md) (общие data-файлы как граница между языками).

## Расширенное содержание (общее)

### Зачем вообще «текстовые языки» в игровом монорепо
Большая часть кода игры — это **данные в текстовом виде**: JSON-уровни, CSV-балансы, SQL-дампы, Markdown-доки, JS-конфиги. Изменения в них чаще всего носят характер **массового однотипного преобразования**: «во всех файлах переименуй поле `hp` в `health`», «собери все `id` сущностей из 40 файлов», «преврати CSV прайса в SQL `INSERT`-ы». Писать под каждую такую задачу полноценный модуль на JS/PHP дорого. Текстовые языки решают это в одну-три строки.

Три семейства кирпичиков:

1. **Потоковые однострочники Unix** — `grep`/`ripgrep` (поиск), `sed` (потоковая замена), `awk` (поля и колонки), `cut`/`sort`/`uniq`/`tr`. Работают построчно, тянут гигабайты, есть везде.
2. **Структурные процессоры** — `jq` (JSON), `yq` (YAML/XML). Понимают вложенность, а не просто строки. Критично, потому что в NEXUS «источник истины» часто JSON/Markdown ([NX-POLY-004](NX-POLY-004-shared-data-files.md)).
3. **Perl** — «швейцарский нож»: полноценный язык, но с regex и обработкой текста в ядре синтаксиса. Берёт задачи, которые переросли `sed`/`awk`, но ещё не дотягивают до отдельного Python-скрипта: многострочный парсинг, миграции с логикой, генерация кода по шаблонам, in-place правки деревьев файлов.

### Философия «велосипед с крылышками»
**Колесо/автомобиль (не переизобретаем):** regex-движок, потоковая модель «строка → преобразование → строка», конвейер `|`, формат «текст как универсальный интерфейс» — всё это придумано в 1970–80-х (Unix, AWK 1977, Perl 1987) и отполировано до блеска. Переписывать это на собственном «генераторе данных» — изобретать квадратное колесо.

**Крылышки (новое измерение поверх):** мы оборачиваем эти древние инструменты в **современный воспроизводимый пайплайн**:
- скрипты-однострочники живут в `tools/` под git, а не в истории чьего-то bash;
- каждая миграция данных — это **идемпотентный, версионируемый, тестируемый** шаг (как миграции БД), а не разовая команда «по памяти»;
- запуск через `make`/`npm run`/CI, вход/выход — общие data-файлы ([NX-POLY-004](NX-POLY-004-shared-data-files.md)) и пайпы ([NX-POLY-003](NX-POLY-003-stdin-stdout-pipes.md));
- `ripgrep` заменяет `grep` там, где нужна скорость, но **семантика Unix остаётся**.

То есть Формула-1 (CI + git + тесты) поверх давно изобретённого автомобиля (Perl + пайп).

## Детали и частные случаи

### Где Perl/текстовые языки реально сильны (с примерами)

**1. Миграция структуры данных (JSON-уровни и конфиги).**
Задача: во всех `level*.js` переименовать поле `hp` → `health`, не трогая комментарии и форматирование.

```bash
# in-place по дереву файлов; -i.bak делает резервную копию; \b — граница слова
perl -i.bak -pe 's/\bhp\b/health/g' games/nexus/v3-3d/data/level*.js
```

Структурная (надёжнее, если данные — настоящий JSON) через `jq`:

```bash
# переименовать ключ hp->health в каждом объекте массива entities
jq '.entities |= map(.health = .hp | del(.hp))' level1.json > level1.new.json
```

**2. CSV → SQL (миграция прайсов из соседнего сайта-проекта).**
В репо есть `ceny_svodka.csv`. Превратить в `INSERT`-ы:

```bash
# awk: $1=name $2=price; OFS не нужен, печатаем готовый SQL. Экранируем кавычки.
awk -F',' 'NR>1 {gsub(/'"'"'/,"'"'"''"'"'",$1);
  printf "INSERT INTO prices(name,price) VALUES ('"'"'%s'"'"', %s);\n",$1,$2}' \
  ceny_svodka.csv > prices.sql
```

То же на Perl, когда нужна валидация и пропуск кривых строк:

```perl
#!/usr/bin/perl
use strict; use warnings;
use Text::CSV;                      # проверенный кирпичик: корректный парсинг CSV
my $csv = Text::CSV->new({ binary => 1 });
open my $fh, '<:encoding(utf8)', 'ceny_svodka.csv' or die $!;
$csv->getline($fh);                 # пропустить заголовок
while (my $row = $csv->getline($fh)) {
    my ($name, $price) = @$row;
    next unless defined $price && $price =~ /^\d+(\.\d+)?$/;  # валидируем
    $name =~ s/'/''/g;              # SQL-экранирование
    printf "INSERT INTO prices(name,price) VALUES ('%s', %s);\n", $name, $price;
}
```

**3. Парсинг логов PHP-бэкенда (`nexus_api.php`).**
Вытащить топ ошибок за сегодня:

```bash
# fatal/error за сегодняшнюю дату, сгруппировать и отсортировать по частоте
rg -N "$(date +%Y-%m-%d).*(PHP (Fatal|Warning)|nexus_api)" storage/logs/*.log \
  | sed -E 's/.*(PHP (Fatal|Warning)[^,]*).*/\1/' \
  | sort | uniq -c | sort -rn | head -20
```

Многострочные stack trace — это уже работа для Perl (склейка строк по записям):

```perl
# режим абзацев (-00): запись = блок до пустой строки; ловим трейсы с "Stack trace"
perl -00 -ne 'print "----\n$_" if /Stack trace/' storage/logs/php_error.log
```

**4. Генерация кода/контента (codegen) по шаблону.**
Сгенерировать заготовки документов вики из списка id (перекликается с [NX-POLY-002](NX-POLY-002-codegen.md) — генерация кода как interop):

```bash
# для каждого id печатаем skeleton .md с YAML-шапкой
awk '{printf "---\nid: %s\nstatus: draft\n---\n\n# %s\n\n## TL;DR\n", $1, $1}' ids.txt
```

**5. Массовый рефакторинг текста через дерево.**
Заменить старый CDN-URL во всех HTML-вариантах игры:

```bash
rg -l 'old-cdn\.example' --glob '*.html' \
  | xargs perl -i -pe 's{https://old-cdn\.example}{https://cdn.nexus.local}g'
```

### Граничные случаи и подводные камни
- **Кодировки.** Русский текст в `database.json`/Markdown — всегда указывай `:encoding(utf8)` (Perl) и `LC_ALL=C.UTF-8`. `sed`/`awk` на «голых» байтах могут испортить многобайтовые символы.
- **JSON нельзя парсить regex’ом надёжно.** Для вложенных структур — только `jq`/настоящий парсер. `sed` по JSON допустим лишь для тривиальных плоских правок.
- **Идемпотентность.** Миграция должна быть безопасна при повторном запуске (`s/\bhp\b/health/` второй раз — no-op, и это хорошо).
- **Windows-окружение проекта.** Репо лежит под `C:\xampp` на Windows. `perl`, `awk`, `sed`, `jq`, `rg` доступны через Git Bash (POSIX-слой); в `cmd.exe`/PowerShell их нет по умолчанию — фиксируй это в README инструментов.
- **`-i` без бэкапа опасен.** Всегда `-i.bak` либо прогон через git (видно diff, откатываемо).

## Предложения и варианты реализации

### Таблица выбора инструмента

| Задача | Лучший кирпичик | Почему | Альтернатива |
|---|---|---|---|
| Найти текст в дереве | `ripgrep` (`rg`) | быстрее `grep`, .gitignore-aware | `grep -r` |
| Плоская замена в файлах | `sed` / `perl -pe` | потоково, in-place | IDE «replace in files» |
| Колонки/CSV без кавычек | `awk` | поля из коробки | `cut` |
| CSV с кавычками/экранированием | Perl + `Text::CSV` | корректный парсинг | Python `csv` |
| Преобразование JSON | `jq` | понимает вложенность | Python `json` |
| YAML-шапки доков | `yq` | YAML-aware | Perl `YAML::XS` |
| Многострочный парсинг логов | Perl (`-00`, `-n`) | режимы записей, regex в ядре | Python `re` |
| Сложная миграция с логикой/БД | **Python** | читаемость, тесты, библиотеки | Perl при «текст важнее логики» |
| Разовый однострочник в терминале | Perl/awk/sed | плотность, скорость набора | — |

### Честный выбор: Perl vs Python vs ripgrep
- **Бери `ripgrep`/`sed`/`awk`/`jq`**, когда задача — это поиск или линейное преобразование потока (90% разовых задач).
- **Бери Perl**, когда переросло `sed`/`awk` (многострочность, in-place по дереву, regex с группами и логикой), но заводить отдельный модуль не хочется. Сила Perl — **однострочники и склеечные скрипты**.
- **Бери Python** ([NX-POLY-001](NX-POLY-001-language-roles.md) уже отдаёт ему генерацию контента), когда нужны: читаемость для команды, тесты, работа с БД/API, структуры данных, повторное использование. **Не превращай Perl-скрипт на 200 строк в «проект» — это сигнал, что нужен Python.**

### Псевдокод: миграция данных как версионируемый шаг
Оборачиваем текстовые кирпичики в идемпотентный, тестируемый шаг (те самые «крылышки»):

```pseudo
// tools/migrations/2026-06-29-rename-hp-to-health.sh
set -euo pipefail
LC_ALL=C.UTF-8

run() {
  for f in games/nexus/*/data/level*.js; do
    perl -i.bak -pe 's/\bhp\b/health/g' "$f"
  done
}

verify() {
  // тест: после миграции 'hp' как самостоятельного поля не осталось
  if rg -q '\bhp\b' games/nexus/*/data/level*.js; then
     echo "FAIL: остались вхождения hp"; exit 1
  fi
  echo "OK"
}

case "${1:-run}" in
  run)    run; verify ;;
  verify) verify ;;
esac
// запуск: make migrate STEP=2026-06-29-rename-hp-to-health
// откат:  git checkout -- games/nexus/*/data/   (или *.bak)
```

### Interop-механизмы (как этот слой стыкуется с остальными языками)
- **Пайпы stdin/stdout** ([NX-POLY-003](NX-POLY-003-stdin-stdout-pipes.md)): `python gen_level.py | jq '.entities|=sort_by(.id)' | perl -pe '...' > level.json`. Каждый язык — звено конвейера, граница — поток JSON-строк.
- **Общие data-файлы** ([NX-POLY-004](NX-POLY-004-shared-data-files.md)): Markdown/JSON как источник истины; текстовые инструменты читают и пишут те же файлы, что JS/PHP, без «своего» формата.
- **Codegen** ([NX-POLY-002](NX-POLY-002-codegen.md)): awk/Perl как генераторы boilerplate (скелеты доков, SQL-`INSERT`, JS-таблицы констант) — текст на входе, текст-код на выходе.

## Что нового и какие кирпичики
- **НОВОЕ:** не язык, а **роль и упаковка**. Перевести разовые текстовые правки из «команд по памяти» в **версионируемый, идемпотентный, тестируемый слой миграций/codegen** монорепо, с честной таблицей выбора инструмента под задачу. Новое измерение = современный пайплайн (git diff, CI-verify, `ripgrep`) поверх классики.
- **Источники:** `c20-proven` (Unix-философия «текст — универсальный интерфейс», AWK 1977, Perl 1987, конвейеры), `humanities` (Markdown как «источник истины» — текст ближе к естественному языку, чем к структуре).
- **Проверенные кирпичики:** Perl + `Text::CSV`/`YAML::XS`, `awk`, `sed`, `grep`/`ripgrep`, `jq`/`yq`, оператор `|`, `xargs`, режимы записей Perl (`-00`, `-n`, `-p`, `-i`).
- **Чего обычно нет (или редко) в игровых проектах:** осознанное закрепление «текстового клеевого языка» как первоклассного слоя архитектуры с явным критерием «когда Perl, когда Python», вместо стихийных bash-однострочников, теряющихся в истории терминала.

## Риски, открытые вопросы
- **Поддерживаемость Perl.** Команда чаще знает Python/JS; Perl-скрипты сложнее читать. **Митигация:** жёсткий лимит — Perl только для однострочников и склейки до ~50 строк; больше — Python. `use strict; use warnings;` обязательны.
- **Кросс-платформенность.** На Windows-репо нужен Git Bash/WSL; голый PowerShell не даёт `awk`/`perl`. Открытый вопрос: дублировать ли критичные миграции PowerShell-версией или зафиксировать Git Bash как обязательную зависимость dev-окружения.
- **Дрейф между регексом и реальной грамматикой.** Парсинг JSON/HTML/JS регексом хрупок. Правило: для структурных форматов — структурные процессоры (`jq`/парсер), regex только для плоского текста и логов.
- **Открыто:** нужен ли единый раннер миграций (`make`/Node-скрипт), который оркеструет шаги и `verify`? Кандидат на отдельный спек — см. [NX-SPEC-001](../40-specs/NX-SPEC-001-build-pipeline.md).
